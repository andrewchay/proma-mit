# 达人稿件三态审核

## 这个 Skill 做什么

代替"不常在线"的我方关键人，自动审核第三方在群里提交的达人稿件并回复。第三方收达人稿件 → 群里提交 → 读取稿件 → 结合 brief + 本群审核口径 → 三态回复，第三方据此转达人修改。

- 🔴 **红卡（硬伤需修改）**：@执行成员（提交人）+ 逐条修改意见
- 🟡 **黄卡（需人工判断）**：@Account成员，拍板争议点
- 🟢 **绿卡（待确认放行）**：@Account成员，确认可发布
- ⚠️ **审核失败**：Agent 无法完成审核 → @Account成员

无 Agent 单方面放行档（绿卡也需 @Account 确认）；**不输出分数**；warning 小问题不写入红卡，下版再提。

## 核心规则（最高优先，判定前必须逐条对照）

**本群审核口径（系统注入 `[本群审核口径: ...]`，优先于 brief 旧措辞）**：
- 字数 200 字左右即可，不按 brief 字数要求（如 300 字），不强制扩充，不计分、不构成红卡
- 关键词埋点：正文语义体现即达标，不强求标题/前 15 字
- 话题标签 `#忘本美学`、`#vonbon忘本甄果` 必须植入（缺失即红卡），数量不限
- 未注入时（直聊）用上述默认口径；群内 @Bot「口径：…」可按群覆盖

**本群 brief（系统注入 `[本群 brief（达人名）: ...]`）**：按注入 brief 对照内容方向，正文主体未承载 brief 核心逻辑即红卡；未注入时按 Step 3 查落盘 brief。

**产品名规则（判定前先归一化）**：产品名/单品名比对前先归一化（去空格/符号差异，词序倒换/同义表述视为等价）——**词序倒换/同义变体（如"山竹渍百香果"↔"百香果渍山竹"）不得判红卡**，仅归入黄/绿卡"可优化"建议对齐 brief 口径；仅当指向池外或不存在产品（真自造名、错字致指向不明）才红卡。

**可优化区块（结合 brief 方向，强制）**：黄卡/绿卡末尾的"可优化（结合 brief 方向，非硬性）"区块**必须对照 brief 方向逐一产出非硬性建议**，不得因放行（绿卡）就省略区块或一律写"无建议"。建议来源四类典型场景：
- 稿件未充分承接 brief 内容方向（场景/叙事/氛围点缺失，如"桌面对决"）
- 配图与封面未覆盖 brief 拍摄建议（张数/首图/构图）
- 品牌名或关键词仅出现在话题标签、未在正文露出
- brief 卖点未强化的可优化点

> **判定前必须先读取并逐条对照核心规则与本群审核口径，禁止凭 brief 印象直接下判定。**

## 何时使用

**✅ 触发（群消息中出现以下任意特征）**
- 提交待审核交付物：初稿 / 改稿 / 终稿 / 成片 / 发布预览 / 请查收 / 请审核 / 辛苦审核 / 审核一下 / 稿件 / 审一下（且消息含 附件/链接/内容锚点，如"稿/片/版/预览/内容/文案"）
- 独立长文案（>=80 字，无链接，含"文案/标题/话题/正文/#"标记）也可视为达人文案审核
- brief 管理："录入brief / 导入brief / 达人brief"

**❌ 不触发**
- 纯闲聊、非文本消息
- 数据汇报 / 发布通知 → 用 `ma-publish-data-track`
- 风险预警（延期/拒付/失联等）→ 直接人工研判，本 skill 不做

## 审核流程

```
稿件(文档链接/文件/消息文案) → 提取文字+图片 → 按达人名匹配 brief
  → 文字审核(强制) + 图片审核(Kimi) → 合并 → 三态回复（标注第 N 版）
```

### Step 0 · 飞书浏览器前置（仅 wiki / 网页链接稿件）

文件与 docx 云文档稿件跳过此步（通常已由系统读取并入库）。

1. `curl -s --max-time 3 http://127.0.0.1:9222/json/version` 检查 CDP 是否开启
2. 未开启 → 群内引导用户启动并登录飞书，二选一：
   - A（隔离配置）：`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome --remote-debugging-port=9222 --user-data-dir=/tmp/chrome_pgy_debug`
   - B（复用主 Chrome）：先退出所有 Chrome，同样命令不带 `--user-data-dir`
3. 自检：`python3 scripts/kol_collector.py --check --port 9222`，需 `[OK] CDP 已开启` + `[OK] 飞书登录态正常`
4. 通过后用 CDP 打开链接读正文 + 提取图片块（只操作自己新建的页面，不关用户浏览器），**滚动到底确认文末话题标签区加载完整后，立即落盘再审核**

### Step 1 · 提取达人名

按优先级从消息中提取：
1. `【XX】` 括号包裹的达人名（如"【忘记加芋泥】初稿已过"）
2. 消息任意位置紧邻稿件关键词的 2-12 字 token（如"梦梦呀的预览看看" → 梦梦呀）
3. 文件提交时从文件名兜底（去扩展名 + 去"初稿/改稿/预览"等后缀）
4. 提取失败 → 达人名为空，审核时用通用框架

### Step 2 · 读取稿件内容（按序降级）

按优先级尝试，失败自动降级下一档（**在线文档/最新提交优先于归档**）：
1. **飞书文档/wiki 链接**：先执行 Step 0，用 CDP 打开链接读正文 + 提取图片块，滚动到底确认文末标签区完整
2. **文件**（docx/txt/md）：解析正文 + 提取 docx 内联图片（视为最新提交内容）
3. **消息内文案**：直接用消息文本
4. **仓库归档核对**：查 `workspace-files/draft-archives/{达人名}/{达人名}_v*.md` 最大版本号，与已读最新内容**核对一致性**——归档含"标签（无）"/`verdict: red` 等缺省或异常标记时，**必须回源在线文档/最新提交复核**（无在线来源时不得直接采信该归档，转人工）；无在线/文件/文案来源时归档可作为稿件主体，但须确认其完整（含文末标签区）
5. 全部失败或内容过短（<30 字）→ **转人工**：群内提示"稿件无法自动审核：{原因}，已转人工审核"，不自动催办

> **完整性确认 + 标签证据锚点（强制）**：任何来源的稿件，**判定前必须确认全文（含文末话题标签区）已加载完整**——快照/解析结果不含文末内容时，需滚动到底/重取后再判定；滚动重取后仍无法确认完整 → 按第 5 条转人工。
> 判定前强制产出**标签比对证据块**（仅草稿自检，**不进群回复**）：逐条列出 brief 必带标签 vs 稿件实际标签（附原文摘录）。
> 下"话题标签缺失"红卡必须同时附「已滚动到底/全文确认」声明 + 文末标签区原文摘录；拿不出证据块或声明 → 不得下该红卡，改按审核失败转人工。

### Step 2.5 · 版本存档（兜底落盘）

稿件全文存档到工作区根 `workspace-files/draft-archives/{达人名}/{达人名}_v{N}.md`（以 `workspace-files/` 为唯一根基准），版本号按 (群, 达人) 最大 version + 1 递增，并追加 `workspace-files/draft-review-state.jsonl` 记录（`{ groupId, influencer, version, archivePath, ts }`）：
- 文件/云文档稿件通常已由系统自动存档，此时直接读 jsonl 的 `version` 作为"第 N 版"
- **系统未入库时（如纯消息文案稿件、读取链路异常）**：Agent 一律自行落盘——按 (群, 达人) 最大 version + 1 写入 `workspace-files/draft-archives/{达人名}/{达人名}_v{N}.md` 并追加一条 jsonl 记录
- **落盘必须全文完整（含文末话题标签区）**：快照/解析结果未含文末时先滚动到底/重取，确认完整后再落盘，禁止截断存档或写入"标签（无）"式缺省标记
- 审核后**回填**该记录 `verdict`（`red` | `yellow` | `green`），不新增记录

### Step 3 · 匹配 Brief（命中即落盘，强制）

- 优先用消息中注入的 `[本群 brief]`；未注入时查 `briefs/{达人名}.md`，未找到则在 `briefs/` 目录内扫描文件名含达人名的 md 文件（如 `briefs/vonbon 忘本甄果 · 第二批达人 Brief 合集.md`）读取后按达人段提取（达人名通常作为小标题出现，如 `莉莉` / `【莉莉】` / `莉莉：`）；仍无 → 读取文件名含 "brief" 的最新 md 作为整份综合 brief 参考
- **补建单达人 brief（强制）**：`briefs/{达人名}.md` 不存在、但从综合 brief 已提取到该达人段时，一律将达人段落盘为 `briefs/{达人名}.md`（仅落盘补建，不合并、不覆盖来源综合文件）
- **产品池提取（强制）**：brief 命中/落盘时自动提取**产品池清单**（该达人合作的全部产品名/单品名，含同义/词序变体写法），供 Step 6 产品名比对使用；比对前先**归一化**（去空格/符号差异，词序倒换/同义表述视为等价）
- **命中即落盘（仅系统未自动入库时）**：从 wiki 链接、文件名不含 brief 关键词的文档、历史会话发现的 brief → 单达人写 `briefs/{达人名}.md`、综合按来源文件名分存 `briefs/{来源文件名}.md`（不合并不覆盖），防止跨会话丢失
- 综合 brief 中提取不到该达人段 → 整份综合 brief 作为参考带入
- 完全未找到 → 按通用投放要求审核，回复注明"未录入 brief，按通用投放要求审核"

### Step 4 · 文字审核（强制，不得跳过）

调用 LLM（复用 ma-content-audit 三维方法论），输入稿件全文 + brief + 本群审核口径，取回 issues（含 `severity`）与 `has_critical`：

| 维度 | 要点 |
|------|------|
| 合规性 | 敏感词、平台规范、广告法合规（**一票否决**） |
| 品牌契合度 | 结合 brief：内容方向、文案卖点、品牌调性 |
| 内容质量 | 结构、逻辑、可读性 |
| 投放执行要点 | 话题 tag 是否落实、发布预览规范 |

**判定前必须先读取并逐条对照核心规则与本群审核口径，禁止凭 brief 印象直接下判定。**

### Step 5 · 图片审核（Kimi 视觉）

- 稿件含图片时，调用 Kimi 视觉模型审核：场景氛围 / 产品特写 / 构图重复 / 摆拍痕迹 / 品牌露出 + 画面质量 / 品牌契合 / 合规
- 用 `KIMI_API_KEY` + OpenAI 兼容协议调 `moonshot-v1-8k-vision-preview`
- 图片审核结果与文字合并：**verdict 取较严重者**，图片问题前置到修改意见
- 未配置 `KIMI_API_KEY` 或调用失败 → 仅用文字审核，该稿按黄卡（需人工判断）处理，注明"N 张图片未审"
- 降级：未配置 Kimi 时可用 MAPro 渠道多模态模型替代

### Step 5.5 · 判定前自检 Checklist（强制）

判定前逐项确认，**任一未过 → 按审核失败转人工**：
1. 全文完整（含文末话题标签区，已滚动/重取确认）
2. 产品池已提取并归一化（词序/同义变体已视为等价）
3. 必带话题标签已逐项比对（标签比对证据块已产出）
4. 品牌名/关键词埋点已核对（正文语义体现）
5. 版本号已确认（在线/最新提交 vs 归档一致，归档无"标签（无）"式缺省）
6. 产品名归一化复核（词序/同义变体已确认未误判为红卡）

清单产出到草稿，**不进群回复**。

### Step 6 · 三态判定与统一回复

```
🔴 红卡 = 有硬伤（命中任一 critical 即红卡）：
   - 合规违规（广告法极限词/虚假宣传/违禁内容）
   - 核心信息错误（卖点/品牌/成分/价格）
   - 产品名/单品名**须可明确对应到 brief 产品池内某一产品**（比对前先归一化：去空格/符号差异，词序倒换/同义表述视为等价，如"百香果渍山竹"↔"山竹渍百香果"）；词序变体/同义表述**不构成红卡**，归入黄/绿卡"可优化"（建议与 brief 口径对齐）；仅当指向池外或不存在产品（真自造名、错字致指向不明）才红卡
   - 正文主体未承载 brief 核心概念
   - 关键话题标签缺失（#忘本美学、#vonbon忘本甄果）
   - 品牌露出缺失
   - 图片硬伤（同质化/不可用/摆拍失真/违禁画面）

🟡 黄卡 = 无硬伤（未命中上述任何一项），但存在需人工判断的争议点（口径冲突/调性存疑/灰色地带）

🟢 绿卡 = 无硬伤、无争议点：稿件可发布，待 @Account 确认放行

⚠️ 审核失败 = 稿件无法自动审核（读取失败/内容过短/LLM 调用失败）→ 转人工，@Account 成员
```

> **输出格式强制（不得违反）**：最终回复必须**严格使用下方四个模板之一**，一字不改模板骨架，仅替换 `{占位符}` 内容。
> 禁止自定义格式——**不得**使用"✅ 审核通过""审核报告""稿件初审通过"等措辞，不得新增段落/章节，不得输出判定依据与过程（话题标签/字数/关键词埋点的逐项说明是判定依据，禁止写入回复；仅"可优化"区块内的判定依据允许输出）。
> 黄卡/绿卡模板末尾的"可优化（结合 brief 方向，非硬性）"区块属于模板骨架，**必须对照 brief 方向逐一产出建议**——每条建议对照 brief 方向与稿件内容差距产出，含优化方向+判定依据；仅确实无方向性差距才输出"- 无建议"，不得省略区块。
> 红卡必须 @执行成员、黄卡/绿卡/审核失败必须 @Account 成员，@ 行缺失即格式违规。

**格式细节**：红卡列全部硬伤（合规一票否决时首条改"⚠️ 合规一票否决：{原因}"）；**产品名词序/同义变体不得列入"必须修改"清单**（归入黄/绿卡"可优化"）；黄卡列全部争议点，无条数限制；每条带锚点（`[图片1]`/`[开头]`/`[标题]`/`[正文]`）；字数按核心规则（200 字左右，不构成红卡）；图片未审红卡照出、黄卡注明"含 N 张图片未审"；无总体建议（可优化区块除外）、无分数；黄卡/绿卡末尾的"可优化（结合 brief 方向，非硬性）"区块必须对照 brief 方向逐一产出建议——每条必须对照 brief 方向与稿件内容差距产出，含优化方向+判定依据，仅确实无方向性差距才输出"- 无建议"。

## 角色识别与 @ 规则

判定优先级：**本群角色名单（系统注入 `[本群角色名单]`）→ 成员名称前缀 → 保守第三方**。

| 角色 | 名单/前缀 | @ 谁 |
|------|---------|------|
| 我方关键人 | Account 成员 / `Account-姓名` | 黄卡/绿卡/审核失败 @ 真实姓名 |
| 第三方 | 执行成员 / `执行-姓名` | 红卡 @ 提交人真实姓名 |

识别方法（在 Step 6 回复前执行）：
1. 优先用系统注入的本群角色名单（`Account 成员：…；执行成员：…`），精确 @ 真实姓名
2. 无名单时按群成员名称前缀归类：`Account-*` / `营销-*` → 我方关键人；`执行-*` → 第三方
3. 无前缀或前缀不明确的成员 → 保守视为第三方，不当作我方关键人
4. 我方可能有多个、第三方可能有多个，均可按名单/前缀列出全部，选择与当前稿件相关的人 @
5. **@ 必须独立置于行首**（如 `@徐旭雯`），不得在标题括号/句中/列表内：飞书卡片仅正文支持 `<at>` 渲染
6. 有名单 @ 真实姓名；无名单用 `@Account-姓名`/`@执行-姓名`；匹配不到降级文字点名

名单维护：@Bot「名单：Account-徐旭雯、执行-青子」按群录入/覆盖，跨群隔离。

## Brief 管理

存储约定：`workspace-files/briefs/{达人名}.md`（单达人）；飞书发来的 brief 文件按来源文件名分存（如 `briefs/{来源文件名}.md`，每份独立、互不覆盖，一份含所有达人的综合 brief 也不例外）。

| 操作 | 触发词 | 动作 |
|------|--------|------|
| 导入 | 录入brief / 导入brief + 文档链接 + 达人名 | 读文档 → 提取达人名+核心要点 → 写入 `briefs/{达人名}.md` |
| 查询 | 达人brief / brief是什么 | 列出该达人 brief 或确认是否存在（含文件名含 brief 的综合版 md） |
| 更新 | 更新brief + 文档链接 | 覆盖写入同名文件 |

brief 文档来源支持：飞书文档/wiki 链接、本地文件、PDF（提取全文，按达人名匹配分 brief 页）。综合 brief（文件名含 brief 的 md）审稿时按达人段匹配。

## 审核失败兜底（转人工 @Account）

Agent 审核失败（稿件无法自动审核）时，按"⚠️ 审核失败"模板 @Account 成员并提示第三方（不自动催办）：
- 稿件读取失败 / 无法解析文件内容
- 内容过短（<30 字）
- 全文完整性/标签证据锚点无法确认（判定前自检清单任一未过）
- LLM 未配置或审核调用失败

群内提示："稿件无法自动审核：{原因}，已转人工审核。"

## 状态存储

以工作区根（`workspace-files/`）为基准：

- `briefs/{达人名}.md` — brief 文档（单达人）
- `briefs/{来源文件名}.md` — 综合 brief 按来源文件名分存（每份独立、互不覆盖）
- `draft-archives/{达人名}/{达人名}_v{N}.md` — 稿件全文存档（历史版本全部保留，审稿**在线/最新提交优先**，归档做一致性核对）
- `draft-review-state.jsonl` — 审核记录（追加 `{ groupId, influencer, version, archivePath, ts }`，Agent 回填 `verdict`）

## 与相关 Skill 的边界

- `ma-content-audit`：提供三维审核方法论，本 skill 在其基础上增加 brief 对照、图片审核、三态分档、版本标注、投放执行要点
- `ma-image-audit`：图片视觉审核（Step 5）
- `ma-publish-data-track`：负责发布后数据（发布记录/报数/异常预警），本 skill 只管审稿
