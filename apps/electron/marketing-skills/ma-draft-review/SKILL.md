# 达人稿件三态审核

## 这个 Skill 做什么

代替"不常在线"的我方关键人，自动审核第三方在群里提交的达人稿件并回复。第三方收达人稿件 → 群里提交 → 读取稿件 → 结合 brief + 本群审核口径 → 三态回复，第三方据此转达人修改。

- 🔴 **红卡（硬伤需修改）**：@本次稿件提交人（发对应稿件的执行方）本人 + 逐条修改意见
- 🟡 **黄卡（需人工判断）**：@Account成员，拍板争议点
- 🟢 **绿卡（待确认放行）**：@Account成员，确认可发布
- ⚠️ **审核失败**：Agent 无法完成审核 → @Account成员

无 Agent 单方面放行档（绿卡也需 @Account 确认）；**不输出分数**；warning 小问题不写入红卡，下版再提。

## 核心规则（最高优先，判定前必须逐条对照）

**本群审核口径（系统注入 `[本群审核口径: ...]`，优先于 brief 旧措辞）**：
- 字数 200 字左右即可，不按 brief 字数要求（如 300 字），不强制扩充，不计分、不构成红卡
- 关键词埋点：正文语义体现即达标，不强求标题/前 15 字
- 话题标签 `#忘本美学`、`#vonbon忘本甄果` 必须植入（缺失即红卡），数量不限
- 未注入时（直聊）用上述默认口径；群内 @Bot「口径：…」可按群覆盖

**本群 brief（系统注入 `[本群 brief（达人名）: ...]`）**：按注入 brief 对照内容方向，正文主体未承载 brief 核心逻辑即红卡；未注入时按 Step 3 查落盘 brief。

**产品名规则（判定前先归一化）**：产品名/单品名比对前先归一化（去空格/符号差异，词序倒换/同义表述视为等价）——**词序倒换/同义变体（如"山竹渍百香果"↔"百香果渍山竹"）不得判红卡**，仅归入黄/绿卡"可优化"建议对齐 brief 口径；仅当指向池外或不存在产品（真自造名、错字致指向不明）才红卡。

**品种辨认类不得凭图片下红卡（强制）**：涉及水果品种/材质/真假等**需人工核对实物**的判断，**不得仅凭图片下红卡**——图片只能判**确定性维度**（构图/数量/氛围/品牌露出/清晰度/画面质量）；品种辨认类问题（如"图片里是否山竹/百香果""是否真实果肉"）一律降为**黄卡"需人工核对实物"**，由 @Account 人工拍板，禁止在红卡"必须修改"清单出现品种辨认类条目。

**强推话术不作为红卡判定条件（强制）**：稿件中出现"必囤/必买/必吃/冲"类强推话术（含变体如"必须囤/一定买/必冲"，例："每次野餐必囤"），**即使 brief 有禁用词要求也不得判红卡**——此类表述不构成硬伤，最多归入黄/绿卡"可优化"，建议改为温和替代表达："会回购/想再吃/每次野餐都想吃"类。"会回购/想再吃/每次野餐都想吃"等温和替代表达同样不作为红卡判定条件。

**可优化区块（结合 brief 方向，强制）**：黄卡/绿卡末尾的"可优化（结合 brief 方向，非硬性）"区块**必须对照 brief 方向逐一产出非硬性建议**，不得因放行（绿卡）就省略区块或一律写"无建议"。建议来源四类典型场景：
- 稿件未充分承接 brief 内容方向（场景/叙事/氛围点缺失，如"桌面对决"）
- 配图与封面未覆盖 brief 拍摄建议（张数/首图/构图）
- 品牌名或关键词仅出现在话题标签、未在正文露出
- brief 卖点未强化的可优化点

**返工核对（上版红卡，强制）**：收到注入的 `[上一版红卡反馈: ...]`（该达人最近一次红卡审核的"必须修改"清单）时**以注入为准**；**未注入时，判定前自查 `draft-review-state.jsonl`（或 `draft-review-feedback.csv`）中该达人（或本稿件链接）最近一次 verdict=red 的审核记录**——查到历史红卡则等同注入处理：判定前**先逐条核对**清单中的硬伤在本版稿件是否已修改，**无论是否已修改，都必须在"达人：X"行后输出"返工项确认"区块**（`返工项确认（上版红卡 {F} 处，已修改 {K} 处）`，`{F}` = 上版红卡总条数、`{K}` = 已修改条数，**无修改项填 0**）：
- 已修改 → 在区块内逐条列出（`- ✅ [{位置}] {硬伤} → 已修改`）
- 未修改 → 该硬伤继续列入红卡"必须修改"清单（@提交人继续返工）；仅当上版硬伤全部已修改、本版又无新硬伤时才可出黄/绿卡
- 返回工项确认（K=0 也输出）是为了让第三方明确知道上一轮红卡的核对已完成
- 未注入且自查无任何历史红卡记录时，不输出"返工项确认"区块

> **判定前必须先读取并逐条对照核心规则与本群审核口径，禁止凭 brief 印象直接下判定。**

## 何时使用

**✅ 触发（群消息中出现以下任意特征）**
- 提交待审核交付物：初稿 / 改稿 / 终稿 / 成片 / 发布预览 / 请查收 / 请审核 / 辛苦审核 / 审核一下 / 稿件 / 审一下（且消息含 附件/链接/内容锚点，如"稿/片/版/预览/内容/文案"）
- 独立长文案（>=80 字，无链接，含"文案/标题/话题/正文/#"标记）也可视为达人文案审核
- brief 管理："录入brief / 导入brief / 达人brief"

**❌ 不触发**
- 纯闲聊、非文本消息
- 数据汇报 / 发布通知 → 用 `ma-publish-data-track`
- 风险预警（延期/拒付/失联等）→ 直接人工研判，本 skill 不做

## 审核流程

```
稿件(文档链接/文件/消息文案) → 提取文字+图片 → 按达人名匹配 brief
  → 文字审核(强制) + 图片审核(Kimi) → 合并 → 三态回复（标注第 N 版）
```

### Step 0 · 飞书浏览器前置 + CDP 抓图（所有飞书云文档链接稿件：docx / wiki / 网页，强制）

**docx 云文档一律文字+图片同审**：文字以系统注入的正文为准（bridge 已读取 docx 纯文本，未注入时以快速抓取的 `text.txt` 为准），配图一律用下方**快速脚本**（`fetch_feishu_fast.py`，单份约 5 秒）抓取，保证懒加载配图不遗漏；wiki / 网页链接同理（正文以 `WebBridgeSnapshot` 核对完整性）。

持久化 Bash 放行规则默认不启用。只有用户已在 `settings.json` 的 `agentBashAllowRules` 中显式加入对应脚本命令前缀时，本步才能免人工确认；未配置时必须正常发起权限确认。**不要用 `curl` 检查 CDP**（curl 属危险命令会触发人工确认，且不属于固化流程）。

1. **自检**：`python3 scripts/kol_collector.py --check --port 9222`，需 `[OK] CDP 已开启` + `[OK] 飞书登录态正常`；未开启 → 群内引导用户启动并登录飞书，二选一：
   - A（隔离配置）：`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome --remote-debugging-port=9222 --user-data-dir=/tmp/chrome_pgy_debug`
   - B（复用主 Chrome）：先退出所有 Chrome，同样命令不带 `--user-data-dir`
2. **快速抓取（首选，秒级）**：输出目录用 `{工作区根}/draft-archives/{达人名}/v{N}-images`（`{工作区根}` = 系统注入的 `[工作区根路径]` 绝对路径），执行：
   `python3 scripts/fetch_feishu_fast.py --port 9222 --url '<稿件链接>' --out '<输出目录>'`
   - 脚本自动：新开页面打开稿件 → 注入 MutationObserver + **高速双程滚动**（先滚到底再回滚，实时收集进入 DOM 的 `[data-block-id]` 文本块与 `<img>`，避免滚动后二次读 DOM 漏块）→ 输出 `text.txt`（正文全文，已滤 UI 噪音/连续去重）+ `raw_texts.txt`（原始）+ **并发下载全部配图**（`context.request` 复用登录 Cookie，单张 50-300KB，8 张约 1-2 秒）+ 写 `images.json`
   - 单份约 **5 秒**；原 `kol_collector.py --extract-images`（逐屏滚动 1-3 分钟）降级为兜底
   - **正文以 `text.txt` 为准**（系统未注入正文时）；仍以 `WebBridgeSnapshot` 核对完整性与文末标签区
   - 检查 stdout 的 `[OK] 配图 N 张` 与 `images.json`；无配图（文档纯文字）则跳过图片审核
   - **页面头像已自动剔除**（`static-resource` 域 v3_0013j_ 资源，不入 `images.json`）
   - **锚点按稿件图序编号（强制）**：`images.json` 序号即稿件图序（第 1 张稿件配图 = 图片1），确保 ma-image-audit `overall_issues.location` 与你的修改意见 `[图片N]` 锚点一一对应
   - **宫格/画廊兜底（强制）**：`images.json` 张数明显少于文档实际配图时，用 `WebBridgeScreenshot` 对宫格/画廊区域截图，作为图片审核补充依据并在修改意见中标注
   - **降级**：快速脚本抓取失败（登录态异常/CDP 无页面/文本为空）→ 用 `python3 scripts/kol_collector.py --extract-images --port 9222 --url '<稿件链接>' --out '<输出目录>'` 兜底
   - 稿件链接含 `&` 等 shell 特殊字符时先做 URL 编码再传入
3. **正文核对**：`WebBridgeSnapshot` 读取页面正文（含文末话题标签区），与 `text.txt`/系统注入正文做一致性核对；不一致以页面为准
4. 确认全文（含文末话题标签区）已加载完整后，立即落盘再审核（落盘根基准见 Step 2.5：使用系统注入的 `[工作区根路径]` 绝对路径，禁止相对路径落到会话目录）

### Step 1 · 提取达人名

按优先级从消息中提取：
1. `【XX】` 括号包裹的达人名（如"【忘记加芋泥】初稿已过"）
2. 消息任意位置紧邻稿件关键词的 2-12 字 token（如"梦梦呀的预览看看" → 梦梦呀）
3. 文件提交时从文件名兜底（去扩展名 + 去"初稿/改稿/预览"等后缀）
4. 提取失败 → 达人名为空，审核时用通用框架

### Step 2 · 读取稿件内容（按序降级）

按优先级尝试，失败自动降级下一档（**在线文档/最新提交优先于归档**）：
1. **飞书云文档/wiki/网页链接（含 docx）**：先执行 Step 0——**文字+图片同审**：文字以系统注入正文或 `fetch_feishu_fast.py` 产出的 `text.txt` 为准（docx 已由系统读取纯文本），配图一律 `fetch_feishu_fast.py` 快速脚本抓取（MutationObserver + 高速双程滚动，单份约 5 秒，下载到 `draft-archives/{达人名}/v{N}-images`），正文含文末标签区用 `WebBridgeSnapshot` 核对完整；失败降级 `kol_collector.py --extract-images`
2. **文件**（docx/txt/md）：解析正文 + 提取 docx 内联图片（视为最新提交内容）
3. **消息内文案**：直接用消息文本
4. **仓库归档核对**：查 `{工作区根}/draft-archives/{达人名}/{达人名}_v*.md` 最大版本号（工作区根 = 系统注入的 `[工作区根路径]` 绝对路径，未注入时用 `workspace-files/`），与已读最新内容**核对一致性**——归档含"标签（无）"/`verdict: red` 等缺省或异常标记时，**必须回源在线文档/最新提交复核**（无在线来源时不得直接采信该归档，转人工）；无在线/文件/文案来源时归档可作为稿件主体，但须确认其完整（含文末标签区）
5. 全部失败或内容过短（<30 字）→ **转人工**：群内提示"稿件无法自动审核：{原因}，已转人工审核"，不自动催办

> **完整性确认 + 标签证据锚点（强制）**：任何来源的稿件，**判定前必须确认全文（含文末话题标签区）已加载完整**——快照/解析结果不含文末内容时，需滚动到底/重取后再判定；滚动重取后仍无法确认完整 → 按第 5 条转人工。
> 判定前强制产出**标签比对证据块**（仅草稿自检，**不进群回复**）：逐条列出 brief 必带标签 vs 稿件实际标签（附原文摘录）。
> 下"话题标签缺失"红卡必须同时附「已滚动到底/全文确认」声明 + 文末标签区原文摘录；拿不出证据块或声明 → 不得下该红卡，改按审核失败转人工。

### Step 2.5 · 版本存档（兜底落盘）

稿件全文存档到工作区根 `<工作区根>/draft-archives/{达人名}/{达人名}_v{N}.md`。**落盘根基准 = 系统注入的 `[工作区根路径]` 绝对路径**（如 `/…/bot/workspace-files/`）；未注入时才用相对路径 `workspace-files/`。注意 `<working_directory>` 是会话目录，**相对路径会解析到会话目录下、导致工作区看不到，必须优先使用注入的绝对路径**。版本号按 (群, 达人) 最大 version + 1 递增，并追加 `<工作区根>/draft-review-state.jsonl` 记录（`{ groupId, influencer, version, archivePath, ts }`）：
- 文件/云文档稿件通常已由系统自动存档，此时直接读 jsonl 的 `version` 作为"第 N 版"
- **系统未入库时（如纯消息文案稿件、读取链路异常）**：Agent 一律自行落盘——按 (群, 达人) 最大 version + 1 写入 `<工作区根>/draft-archives/{达人名}/{达人名}_v{N}.md` 并追加一条 jsonl 记录
- **落盘必须全文完整（含文末话题标签区）**：快照/解析结果未含文末时先滚动到底/重取，确认完整后再落盘，禁止截断存档或写入"标签（无）"式缺省标记
- 审核后**回填**该记录 `verdict`（`red` | `yellow` | `green`），不新增记录

### Step 3 · 匹配 Brief（命中即落盘，强制）

> 本步所有 `briefs/` 相对路径均以系统注入的 `[工作区根路径]` 绝对路径为基准（未注入时用 `workspace-files/`；`<working_directory>` 是会话目录，禁止在其中创建 briefs）。

- 优先用消息中注入的 `[本群 brief]`；未注入时查 `briefs/{达人名}.md`，未找到则在 `briefs/` 目录内扫描文件名含达人名的 md 文件（如 `briefs/vonbon 忘本甄果 · 第二批达人 Brief 合集.md`）读取后按达人段提取（达人名通常作为小标题出现，如 `莉莉` / `【莉莉】` / `莉莉：`）；仍无 → 读取文件名含 "brief" 的最新 md 作为整份综合 brief 参考
- **补建单达人 brief（强制）**：`briefs/{达人名}.md` 不存在、但从综合 brief 已提取到该达人段时，一律将达人段落盘为 `briefs/{达人名}.md`（仅落盘补建，不合并、不覆盖来源综合文件）
- **产品池提取（强制）**：brief 命中/落盘时自动提取**产品池清单**（该达人合作的全部产品名/单品名，含同义/词序变体写法），供 Step 6 产品名比对使用；比对前先**归一化**（去空格/符号差异，词序倒换/同义表述视为等价）
- **命中即落盘（仅系统未自动入库时）**：从 wiki 链接、文件名不含 brief 关键词的文档、历史会话发现的 brief → 单达人写 `briefs/{达人名}.md`、综合按来源文件名分存 `briefs/{来源文件名}.md`（不合并不覆盖），防止跨会话丢失
- 综合 brief 中提取不到该达人段 → 整份综合 brief 作为参考带入
- 完全未找到 → 按通用投放要求审核，回复注明"未录入 brief，按通用投放要求审核"

### Step 4 · 文字审核（强制，不得跳过）

调用 LLM（复用 ma-content-audit 三维方法论），输入稿件全文 + brief + 本群审核口径，取回 issues（含 `severity`）与 `has_critical`：

| 维度 | 要点 |
|------|------|
| 合规性 | 敏感词、平台规范、广告法合规（**一票否决**） |
| 品牌契合度 | 结合 brief：内容方向、文案卖点、品牌调性 |
| 内容质量 | 结构、逻辑、可读性 |
| 投放执行要点 | 话题 tag 是否落实、发布预览规范 |

**判定前必须先读取并逐条对照核心规则与本群审核口径，禁止凭 brief 印象直接下判定。**

### Step 5 · 图片审核（Kimi 视觉）

- 稿件含图片时，调用 Kimi 视觉模型审核：贴合 brief 内容方向 / 三图结构（场景图、产品特写图、产品整体图）/ 场景氛围 / 产品特写 / 构图重复 / 摆拍痕迹 / 品牌露出 + 画面质量 / 品牌契合 / 合规
- 用 `KIMI_API_KEY` + OpenAI 兼容协议调 `moonshot-v1-8k-vision-preview`
- 图片审核结果与文字合并：**verdict 取较严重者**，图片问题前置到修改意见
- 未配置 `KIMI_API_KEY` 或调用失败 → 仅用文字审核，该稿按黄卡（需人工判断）处理，注明"N 张图片未审"
- 降级：未配置 Kimi 时可用 MAPro 渠道多模态模型替代

### Step 5.5 · 判定前自检 Checklist（强制）

判定前逐项确认，**任一未过 → 按审核失败转人工**：
1. 全文完整（含文末话题标签区，已滚动/重取确认）
2. 产品池已提取并归一化（词序/同义变体已视为等价）
3. 必带话题标签已逐项比对（标签比对证据块已产出）
4. 品牌名/关键词埋点已核对（正文语义体现）
5. 版本号已确认（在线/最新提交 vs 归档一致，归档无"标签（无）"式缺省）
6. 产品名归一化复核（词序/同义变体已确认未误判为红卡）

清单产出到草稿，**不进群回复**。

### Step 6 · 三态判定与统一回复


## 角色识别与 @ 规则

判定优先级：**本群角色名单（系统注入 `[本群角色名单]`）→ 成员名称前缀 → 保守第三方**。

| 角色 | 名单/前缀 | @ 谁 |
|------|---------|------|
| 我方关键人 | Account 成员 / `Account-姓名` | 黄卡/绿卡/审核失败 @ 真实姓名 |
| 第三方 | 执行成员 / `执行-姓名` | 红卡 @ 本次稿件提交人（[发送者] 即发稿件的执行方）本人真实姓名 |

识别方法（在 Step 6 回复前执行）：
1. 优先用系统注入的本群角色名单（`Account 成员：…；执行成员：…`），精确 @ 真实姓名
2. 无名单时按群成员名称前缀归类：`Account-*` / `营销-*` → 我方关键人；`执行-*` → 第三方
3. 无前缀或前缀不明确的成员 → 保守视为第三方，不当作我方关键人
4. **红卡 @ 对象 = 本次稿件提交人本人**（消息 `[发送者]` 字段，即群里发对应稿件的那个执行方）；执行方多人时必须 @ 提交人本人，**禁止** @ 名单中全部执行成员或任意挑一个；黄卡/绿卡/审核失败按名单/前缀 @ Account 成员
5. **@ 必须独立置于行首**（如 `@徐旭雯`），不得在标题括号/句中/列表内：飞书卡片仅正文支持 `<at>` 渲染
6. 有名单 @ 真实姓名；无名单用 `@Account-姓名`/`@执行-姓名`；匹配不到降级文字点名

名单维护：@Bot「名单：Account-徐旭雯、执行-青子」按群录入/覆盖，跨群隔离。

1. **过滤页面头像**：当前脚本仅按 `naturalWidth >= 200` 筛选配图，飞书页面头像/编辑者头像可能大于 200px 被误收为稿件图。修正方向：提取 JS 中按 alt 关键词（头像/avatar）、元素尺寸、DOM 位置/祖先特征排除头像。未修前，Agent 必须按 Step 0 规则人工剔除头像后编号。
