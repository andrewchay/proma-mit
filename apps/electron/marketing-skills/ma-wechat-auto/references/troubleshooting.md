# 踩坑记录（微信 4.x · macOS · 坐标+OCR 路线）

原理：坐标点击（`cliclick`）+ 按键注入（System Events）+ 截图 OCR（Vision）。
微信 4.x **不暴露辅助功能树**，所以不用"查找元素"，改用"截图 → OCR 定位 → 点击"。

## 一、实现层踩坑（改脚本前必读）

1. `CGEventPost` 注入的 **Return 不被微信 4.x 接受** → 按键统一走 `osascript System Events key code`
2. 鼠标点击用 **cliclick**（已验证可用），路径固定在 `/opt/homebrew/bin/cliclick`
3. 中文 / emoji **只能走剪贴板粘贴**（`⌘V`），直接键入会乱码
4. 微信**搜索结果在独立浮层窗口**（`layer=3`），截主窗口看不到
5. **会话列表会因新消息重排** → 点行前必须**重新 OCR**，且发送前**校验标题**
6. 聊天区 / 输入框分界 ≈ 窗口底部往上 **275pt**（`input_top()`）
7. 消息方向用**气泡底色**判断：微信绿 = 我方，白/灰 = 对方（`_is_outgoing()`）
8. **久未互动的会话会被挤出可见列表**（会话按最近活跃排序，只显示最上面约 8 条）→ 仅靠"点可见会话行"会**找不到人**。`open_chat()` 已做兜底：可见列表里找不到时，自动点搜索框搜索，在浮层里点「联系人」区**最上面那条命中**（`open_chat_by_search()` + `find_overlay()` + `capture_wid()`）。**达人建联尤其依赖这条**，因为达人常常隔很久才回、会话早沉底了。
9. **绝不要在本人正在用微信时跑自动化** —— 脚本会激活微信、注入点击与 `⌘V` 粘贴，和手动操作会互相打架（可能把正在编辑的草稿发出去、或点错会话）。**跑之前必须先确认用户此刻不用微信、可以交出控制权。**
10. **语音消息的「转文字」必须悬停才出现** → `convert_voices()` 先把鼠标移到每个语音气泡上，再找并点「转文字」（转换约 2 秒后出文字，文字会留在聊天里，之后 `read` 直接可读）。**我方发出的语音微信不提供「转文字」**，只有对方发来的能转；所以对方发语音时，应先 `voices` 再 `read`。已转换过的语音不会再出现按钮，不会重复点。
11. **信息面板 / 设置窗口会污染 OCR** —— 聊天若开着右侧「聊天信息」面板，面板里的「置顶聊天 / 清空聊天记录」等会被当成消息读出来。`read` 前先确认没有面板打开（点聊天右上角「…」或点空白处收起）。
12. **"发送成功"必须以"文字进入输入框"为准** —— 目标会话**本来就开着**时，标题校验会**误判成功**（点击其实没落到输入框，`⌘V` 落空、`Enter` 空按）。`send_message()` 已改为：点输入框确保焦点 → 粘贴 → **确认输入框里出现该文字** → 才回车；没落进去自动重试。
13. **右键菜单不可用** —— WeChat 4.x Mac 对 `cliclick rc:` 的右键不响应（语音和消息都试过），所以**撤回 / 转发等右键操作无法自动化**，只能人工做。
14. **会话行 y 过滤要留够顶部空间** —— 曾用 `oy+90` 漏掉列表最顶部的会话（如置顶 / 最新的那条），已统一为 `oy+60`。窗口被改过大小 / 位置时（如 728×650），所有坐标会自动重算，但边界阈值要复核。
15. **「搜一搜」会抢走主窗口（严重）** —— 一旦打开「搜一搜」，会多出一个**面积更大的** `layer-0` 微信窗口（名字含「搜一搜」/「窗口」），而旧的 `find_main_window` 只按面积取最大 → **选错窗口**，导致之后所有截图 / OCR / 坐标全部错。已改为**按窗口名排除「窗口 / 搜一搜」，并优先取名字正好是「微信」的**。关闭搜一搜：点它标题栏标签上的 `✕`（点红绿灯无效）。
16. **不要用 ⌘F 打开聊天搜索** —— `⌘F` 有时会打开「搜一搜」全屏页而不是聊天搜索浮层（不稳定，是 #15 的诱因）。已改为**直接点会话列表顶部的搜索框**（位置相对窗口稳定，见 `search_box_point()`）。
17. **搜索浮层里必须跳过网页结果** —— 浮层结构为「搜索网络结果（网页建议）→ 功能（联系人 / 公众号）→ 聊天记录」，**网页建议里也会出现同名文字**。取最上面的命中会点成网页搜索。正确做法：**跳过「功能」标题以上的命中**，取功能区最上面那条（`open_chat_by_search()` 已实现）。
18. **预览对比要防 OCR 抖动** —— 会话预览的 OCR 偶尔会**瞬时**读出不同结果，导致误报"有新消息"→ 对没变化的会话做无谓读取（白抢一次焦点）。`poll_replies.py` / `auto_daemon.py` 已加"复读确认"：疑似变化时隔 0.6s 再读一次，**两次都变**才算有新消息。

## 二、环境层踩坑

- 缺**屏幕录制**权限 → 截图为空（`wx_probe.py` 会明确提示"很可能是缺少屏幕录制权限"）。
- 缺**辅助功能**权限 → `osascript` 注入按键静默失败（无报错，但没反应）。
- 授权后必须**重启一次**对应应用（终端 / MAPro）。
- 机器上常装了多个 Python：**确认 `python3` 与安装 pyobjc 的那个解释器是同一个**——守护进程后台启动用的是 `sys.executable`（即拉起它的解释器），解释器不一致会报 `No module named 'Quartz'`。
- 微信主窗口被关闭（只剩菜单栏图标）→ `ensure_window()` 会自动 `open -a WeChat` 拉起，但需要几秒。

## 三、守护进程（auto_daemon）相关

- 守护进程**不依赖 MAPro 开着**，是独立 Python 进程；MAPro 只是负责把它拉起来。
- `--stop` 对后台运行（有 `daemon.pid`）发 `SIGTERM`，正常 5 秒内退出（不会等满一个间隔）；对前台运行（无 pid）写 `state/daemon.stop` 停止标记。
- 若 `state/daemon.pid` 残留但进程已不存在，`--status` 会提示"pid 文件残留，可安全忽略"。
- **跑之前**：确认此刻不用微信（会周期性抢焦点）；确认 `watch` 名单正确；先 `--once --dry` 演练。
