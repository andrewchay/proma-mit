## 1. 核心选择

借鉴 Project Shepherd 的**跨角色协调、依赖规划、主动风险处理、诚实汇报和带方案的升级**，将其作为项目 Owner 的行为框架。

不把其角色提示词当作可运行系统。它没有提供持久任务状态、执行授权、费用上界、版本幂等、真实验证和恢复实现；这些仍由 Gravitas 的确定性服务承担。

不采用其“95% 按时交付”“90% 风险提前化解”等数值作为当前承诺，没有样本和计量就不宣称达成。不照搬组织层级、会议节奏、复杂项目章程或大量人工报告。

## 2. 从 Shepherd 到 Gravitas Owner

| 参考职责 | Gravitas 的具体设计 | 用户承担的决定 |
|---|---|---|
| 项目启动与章程 | 从目标整理精简项目简报：目标、成果、标准、已知约束、假设与待确认事项 | 确认目标与关键取舍，不手填一整份章程 |
| WBS、依赖和关键路径 | 提出最小必要任务与可并行项，说明依赖理由与里程碑；只有真实工期证据才给关键路径预测 | 对明显范围/优先级变化作决定 |
| 团队与资源协调 | 按能力、启用状态、授权与可用性推荐角色；系统绑定真实员工 ID，不能虚构可用团队 | 存在成本/能力/位置冲突时确认方案 |
| 执行监督 | 项目事件触发对账，Owner 针对真实变化决定下一步；正常授权内自动推进 | 不逐条催办或重复点击开始 |
| 风险管理 | 识别依赖缺失、反复失败、预算/时间风险；提出可执行恢复方案 | 仅授权变化或业务取舍需要人类批准 |
| 透明沟通 | 常规进展只摘要；需要人时给上下文、建议、备选与影响 | 回答一个有明确判断意义的问题 |
| 质量门禁与交接 | 确定性验证/技术评审/业务验收分别记录，聚合成果并直接打开准确版本 | 验收成果，确认必要应用/发布 |
| 收尾与经验 | 汇总目标达成、剩余风险、真实费用、证据引用与后续建议 | 决定是否关闭项目或提出新目标 |

## 3. Owner 的产品身份与分工

AI Owner 是**项目级管理职责**，不是另一个需要人类逐任务指派的普通 AI 员工。首版建议使用 Supervisor / orchestrator 模式：一个项目级 Owner 管理有限的专业执行角色，通过受控命令调用现有服务。

- Owner 管“目标、计划、资源选择、推进和问题升级”；专业角色管“做出成果”；人类是 Sponsor / 授权者 / 验收者。
- 不要求每个任务都多 Agent：简单任务可由一个执行角色完成；技术评审角色只在类型/质量策略要求时引入，控制协调成本。
- 不通过新增员工 bypass 或任意工具委派实现 Owner 自治。既有 Pilot 若禁用 Runtime 子代理委派，首版继续遵守；专业任务通过既有受控员工执行路径组织。
- Owner 的显示身份不等于数据库中的任务 assignee/审批 actor。现有执行负责人、Reviewer、人类权限保持权威；新 Owner 绑定方式由 AO-02/05 设计核验。
- 不为 Owner 建立一套与项目服务并行的私有任务表。新目标/计划版本元数据与既有任务如何关联，核验存储契约后设计迁移。

## 4. 管理循环：不是聊天后一次性生成计划

```text
目标/答复/任务结果/交付变更/授权变更/恢复信号
  → 读取项目级权威快照（含版本、依赖、真实费用与开放事项）
  → 确定性服务过滤：可继续 / 已处理 / 失效 / 不允许
  → 必要时调用 Owner 模型：澄清、计划、分工、失败分析或调整建议
  → 输出结构化建议，绑定项目、来源/计划版本与证据引用
  → 确定性命令校验：身份、依赖、范围、授权、预算、幂等
  → 授权内执行下一步；否则形成带建议的人类请求
  → 保存权威结果和审计，等待下一个相关变化
```

**避免无效模型循环：** 纯状态刷新、重复事件、已知预算耗尽等可由确定性规则处理。模型只在目标理解、方案选择或新问题需要推理时调用，规划成本也计预算。没有新事实或明确重试授权时，不反复派发同一个失败动作。

在途执行、未知费用和未核验停止需要单独对账；Owner 可以解释并提议处理，但不能用一句“已解决”改变账本或运行事实。

## 5. Owner 的最小输入/输出契约（概念设计）

### 输入：系统组织，不要求人手工填写

- 项目/单任务目标、约束、用户明确反馈；上下文中区分事实、假设和未知。
- 目标/计划版本、权威任务/执行/交付引用；可见资料和权限边界。
- 真实角色目录、能力范围、Runtime 支持、工作位置与预算有效性。
- 已提交成果、验证证据、失败原因、依赖阻塞与待人决定事项。

### 输出：结构化建议，不是任意执行代码

| 输出 | 必需内容 | 生效条件 |
|---|---|---|
| 澄清请求 | 缺什么、为什么会改变方案、推荐答案或选项 | 确需人类决定；已有上下文充分时不重复询问 |
| 项目简报 | 目标、成果、标准、约束、假设、范围排除项 | 人确认关键目标/取舍；未知不自动补成事实 |
| 计划提案 | 任务目的、成果/标准、显式依赖、推荐角色、成本/风险边界、计划版本 | 结构与身份校验通过，确认与授权分别处理 |
| 下一步建议 | 精确任务/来源版本、动作理由、前提、预计副作用 | 受控服务重新核验后执行，不信任模型的“已授权”说法 |
| 变更请求 | 新旧方案差异、原因、费用/范围/期限影响、推荐与备选 | 超授权或关键变化需人确认，旧确认作废 |
| 成果汇报 | 成果引用/版本、标准覆盖、验证等级、剩余风险与待验收项 | 引用可回到权威记录；不凭模型自述判成功 |

真实类型名、IPC 和存储结构在 AO-02 完成后定，不把此概念表当成现有接口契约。

## 6. 默认交互：用户只承担有意义的决定

### 项目目标例子（非代码）

人类：“梳理这款产品的定位，形成可评审的方案。”

Owner 应从授权资料提出：核对目标人群/市场与现有资料 → 梳理竞争与差异 → 形成定位选项 → 对照标准评审 → 汇总推荐方案。只在资料缺失或业务选择会改变路线时追问。资料检索、模型规划和外部信息访问都须有对应权限与预算，不假设已存在非代码执行器。

计划确认卡展示“我准备如何达到你的目标”，不展示要求手填的文件名和员工 ID。Owner 提出角色与资料需求，用户核对关键范围、成果标准和预算。

### 单任务例子（代码）

人类：“报价不能接受负数量，修复后保持正常行为。”

Owner 根据可访问仓库定位实现与测试，提出修改范围和验证方法；用户确认副作用范围，系统内部再冻结路径。Review 显示结果和证据，代码 Diff 作为该类型的专业附件。

### 必要询问例子

不是：“失败了，请自行配置工作区。”

应是：“原工作位置不在当前授权范围，无法继续。我建议使用已绑定的 A 工作区；若必须使用 B，需要补充授权。请选择 A，或申请 B。”

该表述只有真实存在 A/B 和可执行授权入口时才能给出，不编造备选项或用提示文案冒充能力。

## 7. 主动性与沟通策略

- 项目内默认呈现：目标/里程碑、当前推进、下一步、成果、待人决定；模型会话和账本是证据详情，不是用户驾驶入口。
- 有新结果就重新评估相关依赖、评审/返工和计划状态；不以“主动”之名无条件每隔几分钟调用模型。
- 常规进展不打断；阻塞、超授权、质量未达标、预计超预算等才提升为明确事项。通知载体与频率需产品选择，不自动发送外部消息。
- 升级必须附建议和影响，而非把所有问题原样甩给用户；用户答复后重新核验版本，自动恢复对应链路。
- 模型不编造工期或成本。没有可靠估算就标为待估计/未知，展示可执行的预算边界和已有实际消耗。
- 人类随时可以解释、改目标、暂停、拒绝、人工接管。暂停/撤权按已有影响面确认和运行中逐项处理契约，不能一键把未知运行标为已终止。

## 8. Review 与项目收尾

通用 Review 是“成果是否达到目标”；研发 Review 的快照、Diff、验证、人工验收和原仓库应用保留为一种适配器。报告/方案等成果使用相应审阅方式，而非为了兼容当前代码路径强制生成 py 文件。

项目关闭建议至少列出：目标与标准覆盖、交付版本与责任、未完成/不支持项、预算实际/预留/unknown、必要后续行动。Owner 可以推荐关闭，不能代替人类验收或删除历史。

经验记录只保存有证据的项目方法与失败模式，不自动改写长期用户记忆、扩大权限、升级模型或宣称成功率提高。
