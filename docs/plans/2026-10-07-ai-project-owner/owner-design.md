# AI Project Owner：独立主动项目管理者设计

生效：2026-10-18，按用户对原始意图的澄清调整。状态：产品与实施基线；以下目标行为尚未完整实现，不作为执行授权或验收事实。

依据：[目标与路线](goals-and-roadmap.md) · [当前实施台账](ledger.md)。本次修正实施重心，复用已有项目/执行服务，不重置历史证据。

## 2026-10-24 职责与实现收敛决议

Owner 是持续负责的项目管理者，AI 员工是执行者。复用普通 Agent 的执行能力时，必须保留 Owner 独立的管理身份、持久项目上下文和主动生命周期。不能把 Owner 降为仅在用户发消息时运行的主 Agent，也不能以后台固定文案或心跳代替 Owner 理解变化后的判断。

| 层 | 保留或复用的能力 | 明确职责 |
|---|---|---|
| Owner 项目管理层 | 独立管理会话、项目状态、开放问题、决策与待跟进事项 | 主动检查项目、理解变化及其影响、制定与调整方案、分派员工、协调依赖、组织检查和返工、主动联系用户 |
| 主动唤醒层 | 应用后台生命周期、持久事件、定时巡检、重启恢复 | 事件及时唤醒；定时巡检补足遗漏事件、停滞和到期跟进；读取真实变化、按项目合并去重，再交给 Owner 判断 |
| 员工执行层 | 现有 Agent 会话、Runtime、流式输出、工具、工作区、文件、权限与执行状态 | 接受 Owner 的明确任务，在授权范围内实施并交付；Reviewer 独立检查准确成果。员工的执行与检查会话可按需追踪 |
| 系统边界层 | 统一预算出口、访问控制、动作幂等、取消及持久记录 | 对动作作确定性校验并记录实际结果；管理层不能用自然语言代替派工、授权或完成事实 |

主动管理循环为：`事件/巡检到期 → 汇总项目事实与变化 → Owner判断影响 → 记录管理决策 → 调用成熟执行接口或主动向用户提问 → 观察实际结果 → 安排下一次跟进`。没有新事件时仍按待跟进时间检查停滞、期限及授权内资料/成果变化；检查无需每次调用模型。没有实质变化时不重复推理、请求或通知。应用退出期间不承诺持续运行，恢复后补查并接回管理责任。

Owner 应主动提出方案更新，说明发现了什么、影响什么、建议如何调整。授权范围内的执行顺序、员工安排、普通方案修订和有界恢复可自行落实并告知；改变用户目标、关键业务取舍或授权边界时，主动提出建议并等待相关决定。需要等待的事项必须有明确对象、原因和下一次检查条件，不能用“我会核对”作为无动作的结束语。

实现上新增统一的 Owner 派工适配入口，接入现有员工执行服务；复用不等于把 Owner 自主权限授予全部员工。项目身份、任务、访问范围、预算及动作身份由服务传递和检查，不靠员工复写哈希或理解长篇后台协议维持正确性。内部协议与面向用户的任务说明分开呈现。已有 SQLite 权威记录与历史回执继续兼容，新旧入口需按项目明确选择，不能并行重复派工或直接删除旧状态链。

### 此轮收敛的完成条件

- 一次目标与自主范围确认后，Owner 无需用户追加“继续”，通过正常员工会话完成最小文件任务、独立检查与原对话交付；流式内容在响应结束前可见。
- 员工失败、成果返回或授权内资料变化后，Owner 主动理解影响并产生实际管理动作，或带原因与建议向用户提问；回复承诺能对应到动作记录。
- 即使遗漏一次事件，定时巡检也能发现停滞或到期事项并接回责任；重复巡检不重复派工、计费或提醒。
- 切页、隐藏窗口和重启后仍保留开放问题、待跟进事项与执行归属；Owner 不接替员工实施，员工不承担项目管理权限。
- 在同一固定包验证真实模型、真实文件与时间行为；即时假响应和单项控制流通过只作为本地证据。

上述是已确认的产品与实施方向，尚未完成实现与验收。

## 1. 产品承诺与职责

每个项目有一个独立、持续负责的 AI 项目管理者（Owner）。用户像使用 Agent 工作空间一样，在一个项目对话中提供目标、约束和必要细节；Owner 负责拆解、组织 AI 员工、发起工作、协调依赖、跟踪风险、组织质量验收与返工，直到目标达成或明确需要人类决定。

用户主动发起目标和反馈；其余管理会话由 Owner 在需要时主动发起。Owner 能发现项目问题，并带着依据、建议与影响来商量。系统不能依赖用户打开页面、按“请求安排”、逐条启动任务或手动刷新来推进。

| 主体 | 负责的内容 | 对用户的呈现 |
|---|---|---|
| 用户 | 目标、约束、关键业务取舍、必要授权；明确约定的最终认可 | 在同一对话答复、修改、确认、暂停或接管 |
| 项目 Owner | 澄清、计划维护、选择和组织团队、员工会话发起、依赖协调、进度/问题感知、检查验收、返工及收尾 | 方案、实质进展、需要商量的问题和成果 |
| 专业 AI 员工 / Reviewer | 按任务及授权执行或独立检查，提交准确版本的成果和依据 | 由 Owner 汇总；用户可按需查看执行详情 |
| 确定性服务 | 项目身份、访问/费用/版本/依赖、幂等、执行与恢复账本、真实结果 | 通过可读业务边界支持确认；技术详情按需查看 |

AI 负责项目质量验收：根据约定标准调用验证、安排独立评审，未达标时授权内返工。不得把每个子任务都交给用户签收。确需人类判断的业务取舍、明确约定的最终认可及副作用授权仍由用户完成，不能由模型冒签。

## 2. 独立身份与持久项目上下文

“独立”指稳定的项目管理身份、持续上下文和可恢复管理责任，不要求每项目独立 OS 进程，也不要求一个永不结束的模型请求。

- Owner 身份与项目唯一关联；管理会话、目标/计划、开放问题、待跟进事项、委托员工任务和交付版本可追溯。员工的执行身份不冒充 Owner 或用户。
- Owner 管理会话与员工工作会话分开。系统按工作类型组织上下文，Owner 根据可验证结果决定下一步，不把全部日志无限追加给模型。
- 重启后由权威项目/任务/执行/交付记录及管理状态重建上下文，恢复前先对账；模型的记忆或自述不能改变任务/费用/验收事实。
- 当前 carrier 绑定、规划 Run 和一次安排提案可以复用，但不自动等于持久 Owner。实施先明确这些对象的映射、旧项目默认停用/待授权行为及兼容方案，避免创建第二套权威任务表。
- 本地配置优先 JSON/JSONL，已有业务 SQLite 继续维护。新增管理状态存储位置及备份/恢复边界在实现前明确，不无迁移替换权威数据。

## 3. 主动管理循环与唤醒

```text
目标发起 / 用户答复或反馈 / 员工交付或失败 / 依赖变化
权限与预算变化 / 到期检查 / 应用恢复
  → 持久记录事件，按项目去重并串行对账
  → 重建当前权威状态、开放问题与可行动边界
  → 必要时由 Owner 推理：问题是什么、下一步做什么、为什么
  → 形成绑定来源版本的管理决策与动作
  → 服务验证 → 授权内组织员工、检查成果、返工或调整
  → 需人时主动发起项目对话；否则继续或等待下一相关事件
  → 保存结果、消费状态与证据，恢复时重新核验
```

### 唤醒必须产生可验证的管理行为

| 触发 | Owner 应做什么 | 验收观察 |
|---|---|---|
| 新目标/目标变化 | 读取已授权资料和团队，必要时集中澄清，提出/修订方案 | 用户不必另发“请规划/请安排” |
| 员工提交成果 | 对照标准检查、调用验证或独立评审，判断依赖/交接/返工 | 不停在“已完成”通知等用户推动 |
| 失败/停滞/依赖阻塞 | 分析影响，执行授权内可行处理或带建议升级 | 问题识别与处理有事实依据和动作记录 |
| 有效用户答复 | 绑定原问题和最新来源，重新核验后恢复对应工作 | 不要求再点准备、开始或续跑；旧/重复答复不重派 |
| 预算/访问变更、暂停/恢复 | 停止不再有效的动作，先对账，判断可恢复范围 | 不复活旧授权、不重放未知动作 |
| 定时检查到期 | 检查真实停滞、期限/风险和待跟进事项 | 无变化时不固定轮询模型或重复追问 |

管理循环运行在应用后台服务生命周期，不能放在项目页面的 React effect 中。Renderer 切页/重载不应停止已获授权的管理；应用退出、休眠或网络不可用时明确暂停，不承诺离线持续云端运行。恢复后先对账再行动。

事件、决策、命令和成果需精确关联；并发唤醒、重复事件及丢失回包不能重复收费、建任务或发会话。确定性可处理的状态无需调用模型；没有新事实或可用授权不反复推理和重试。

## 4. 自动组织现有团队

Owner 优先读取项目可用的现有员工、能力、访问范围、工作区、Runtime/工具支持与可用状态，自主选择并解释安排。需要执行时由 Owner 发起准确员工会话、跟踪完成并组织交接。

- 日常选人、任务拆分、依赖和 Reviewer 安排由 Owner 决定；多个可胜任员工不构成必须让用户选人的理由。
- 角色名称/模板是能力证据的一部分；不能仅因模板不完全相等就忽略实际能力，也不能仅凭模型声称胜任就授予能力。
- 不将执行者与 Reviewer 必须使用相同渠道/模型/Runtime作为产品要求；实际支持组合由权限、工具、成果接口及独立性契约判断。当前硬限制需逐项适配和验证，在代码改造前仍有效。
- `general`/`controlled`/`development` 等分类和 carrier 隔离规则是既有实现边界。需先核验现有员工能否受控接入，不能为“自动调用”静默改员工权限或绕过 profile 门禁。
- 缺少能力、访问范围或可用预算时，Owner 说明具体缺口、可行方案和影响，在同一对话请求必要决定。不能把用户送回团队页逐项排班作为默认恢复路径。
- 简单任务不强制制造多员工流程；有独立评审要求时由系统保证身份和产物隔离。Owner 可以组织或使用验证工具，不凭自己的文字自我通过。

## 5. 一个对话框的默认交互

```text
用户：目标、约束和可用资料
Owner：必要澄清，或直接给出方案与执行边界
用户：修改/确认必要细节与授权
Owner：自己组织团队并推进，汇报实质变化
Owner：发现需商量的问题，主动给出建议和影响
用户：答复
Owner：自动续跑、检查、返工，提交成果与验收依据
用户：需要时提出修改意见或完成约定的最终认可
```

默认只呈现项目 Owner 对话。方案、成果、必要授权使用对话内卡片；内部任务、员工执行会话、暂停准备、登记/重验、Run/receipt/hash/token/协议/内部状态机均不要求用户操作或理解。排障和审计允许用户按需打开，但不能成为日常必经路径。

Owner 自主决策正常分工和授权内推进。只有缺必要事实、关键业务取舍、需要新增权限/预算，或明确约定由人认可时才提出问题。每次协商包含具体问题、当前依据、推荐方案、备选与影响；同一问题合并、去重，不能持续打扰。规划及日常管理模型请求使用项目已确认的 Provider 和费用边界主动完成，不逐请求打断用户；没有可核验的费用上限或授权时，Owner 暂停并只询问补齐该边界所需的决定。

用户可随时问进度、补资料、改目标、暂停、拒绝或接管。Owner 将反馈关联准确项目与交付版本，说明实质变更及必要授权影响，不能要求用户手动找到 Task Goal 和新规划入口。

全局提醒只把用户带回该项目对话；打开页面后需能看到相同问题/成果。纯 toast 或仅项目页内监听不构成主动管理。常规进度留在对话，不逐工具动作弹窗；外部消息渠道须另有授权。

## 6. 有界委托与内部执行工具

用户可以在对话中确认一份明确的管理委托，覆盖目标/范围、可用团队/资料和工作区、费用与模型请求次数、期限、返工边界、需人决定及允许副作用。Owner 在有效委托内自主发起管理和员工请求，不要求逐个内部模型调用再次推动。

用户确认成果范围及必要执行边界时，可一次确认清楚表达的项目级范围、费用额度、资料权限和期限；同一确认是范围内开工许可。后端仍分别记录和校验各项边界，不能以简化界面降低控制。规划/管理推理计入该项目预算，并在授权内由 Owner 主动调用；不把每次内部模型请求另做一张用户确认卡。既有逐请求门禁、原生确认和敏感工具审批继续适用于尚未纳入项目级授权的动作，以及超出已确认边界的动作。

授权内的日常重新分工、交接和有限返工由 Owner 处理；超范围、预算/权限扩大、关键业务决定及约定副作用需用户确认。计划/来源变化后核对授权覆盖，不默认沿用失效许可，也不把每个内部变化都变成人工表单。

复用已有准备、材料化、重验证、grant/command/request、执行、Review、对账、停止和恢复服务。Owner 输出结构化意图并经权威服务调用，不能通过直接改库或任意工具委派冒充完成。不建立与业务服务平行的私有任务账本。

unknown 费用和未核验停止如实保留；判断是否阻断按既有费用/停止契约和实际可用额度处理，不能为了推进伪造结算。Provider 估算、账户余额和独立账单分别记录。管理预算耗尽时停止新增付费动作并给建议。

## 7. Owner 负责质量验收与收尾

目标阶段由 Owner 形成可判定的标准并集中确认必要业务含义。执行阶段由 Owner 跟踪标准覆盖、组织验证和独立评审；不合格时在允许次数/范围内返工，次数耗尽或业务标准含糊时再升级。

- 代码：Owner 自主定位授权源码和测试、安排隔离修改、内部运行约定验证、让 Reviewer 读取精确执行产物；原仓库应用或发布按相应副作用确认。
- 非代码：Owner 按资料与目标核对论据、完整性及可用性；区分引用、推断与未知。Reviewer 认可不等于所有事实已经外部证实。
- 检查结论绑定准确交付版本，执行完成、独立检查、质量验收、人类认可、应用/发布分别记录。模型自述和工具成功回执不能替代成果质量证据。
- 收尾汇总目标覆盖、准确成果、检查依据、已接受限制、真实/预留/未知费用和剩余事项；符合预先约定条件时 Owner 组织收尾，必须人类认可的项目再提出明确请求。
- 修改意见进入同一对话，Owner 维护计划与成果新版本并续接执行，保留旧版本/失败/审批，不默认让用户重新配置项目。

## 8. 按实际行为验收

当前产品验收以 [Ledger 的唯一 Owner 责任旅程](ledger.md#验收设计owner-对一个项目负完整责任)为准；既有 AO/AO-A/AO-G 编号与历史通过仅作追溯索引，不代表当前产品旅程通过。

最小完整场景：用户给“梳理产品定位，形成可评审方案”及边界。Owner 主动组织现有团队、发起执行、发现一处质量问题并安排返工、主动提出一个真实业务问题，用户答复后自动续跑并提交经检查的成果。再在代码目标中验证同样职责，并补一次反馈后的新版交付。所有介入按实际原因记录，不人为制造不必要询问或返工以凑数量。

| 观察项 | 通过条件 | 不满足的替代证明 |
|---|---|---|
| 持续负责人 | 同一项目上下文和管理责任能跨页/重启恢复 | 只有 carrier 名称或多条独立 Run |
| 主动推进 | 员工交付/异常/答复等事件触发管理判断与动作 | 只有轮询展示或完成通知 |
| 团队组织 | Owner 自己选人、发起会话、安排依赖和评审 | 用户逐人选择或点“请求安排” |
| 质量负责 | 标准对应真实检查与准确版本，失败授权内返工 | 模型宣称已完成或每条任务等人签收 |
| 用户体验 | 单一对话，必要协商和授权可读，答复自动续跑 | 把多个配置模块简单折叠 |
| 可靠性与边界 | 重复/并发/恢复/失效答复不重派，预算/撤权有效 | 单次成功演示或测试数量 |

正常授权范围内人工流程推动次数目标为 0；必要澄清、业务决定、授权和约定最终认可另记。没有新行为改动时不重复全套验证；最终固定候选统一回归并进行两类真实受控验收，证据缺口显式保留。

## 9. 现状与实施顺序
