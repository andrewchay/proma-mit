# Owner 目标与计划持久化设计：首片边界

日期：2026-10-07 GMT+8。用户在 01:26 GMT+8 认可原型并要求继续。状态：目标草案的建表/读取/保存/历史服务已实现并隔离测试；计划持久化、来源/角色适配、IPC/UI 尚未接通，AO-02 继续核验。下文涉及未来计划确认/执行的部分仍为提案，不构成执行授权或新增安全契约审批。

## 1. 本批已核验事实

- `project-sqlite-store.ts` 中已有 `projects`、任务及 `project_chain_revisions`；项目链在同一个项目数据库保存版本化 payload。`project-chain-service.ts` 负责身份/归属、expectedRevision 与提交后通知。
- `goal-service.ts` 的长期 Goal 为独立 JSON 目标/Todo 层；`goal-runtime/goal-coordinator.ts` 为会话级 AgentGoal/检查点/续跑层。
- 目前没有核验出从项目目标到 Owner 计划、确认、权威任务落地的完整映射；不能将现有 Goal quota 或 active 状态当成 Pilot 授权。
- `project-owner-planning.ts` 已提供输入规范化与提案解析，但没有持久化角色目录、费用或上下文读取能力。

## 2. 建议：项目数据库中的附属版本记录

优先在现有项目 SQLite 数据库追加 `project_owner_revisions`，保存项目/单任务的目标与计划快照。它是项目规划元数据，不保存另一套 Todo、execution 或授权账本。

概念键：`(project_id, subject_key, revision)`。`subject_key` 由主进程根据项目目标或真实任务 ID 派生，不能接受任意客户端键；不用 nullable task_id 做唯一性主体，避免 SQLite NULL 唯一性语义漏掉冲突。

快照概念内容：

- `revision`：整个 Owner 规划记录的并发版本，每次有效写操作追加。
- `goalVersion`：目标、约束或验收标准发生实质变化才递增。
- `goalBrief`：已有项目/可选真实 taskId、目标、约束、标准。
- `plan`：可选提案内容、独立 planVersion、目标版本、状态（proposed / confirmed / stale）。
- `planningContext`：主进程读取的来源/角色目录/项目链版本或指纹，用于校验规划期间上下文变化。
- `actor`、时间和变更原因：由主进程确定；不能让模型或客户端冒充人类确认。

计划自身不保存“执行已授权”字段；执行授权与费用仍以现有控制面权威记录为准，后续引用计划版本/指纹的增量契约单独审查。不能复用一个 planVersion 冒充 goalVersion、chainRevision、grant revision 或 task.updatedAt。

## 3. 首个可交付的服务命令（不收费、不派发）

| 命令 | 主进程校验 | 可发生的副作用 |
|---|---|---|
| 读取当前草案/历史 | 项目存在、单任务属于当前项目 | 只读，不自动建草案、不唤醒派发 |
| 保存目标草案 | expectedRevision、输入契约、项目/任务归属；目标版本由服务生成 | 追加草案；改变目标使既有计划失效，不创建权威任务 |
| 保存计划提案 | expectedRevision、目标版本、权威可用角色与上下文指纹、DAG/成果标准；模型只提供已允许字段 | 追加 proposed 计划；不确认、不授权、不创建任务 |
| 确认指定计划 | 当前 planVersion、目标/上下文版本、已启用 local-user actor | 追加 confirmed；仅认可计划内容，不授权、不派发 |

模型规划调用不属于这组无费用服务。后续 Provider 接入必须先增加“规划费用/资料访问授权”门禁，再执行调用，返回结果经过上述提案边界。缺渠道、预算或角色池时允许保存目标，不能调用模型或编造已配置角色。

首个服务切片可以只实现“读取/保存目标草案”，计划持久化再接；不要为了一次交付同时增加 Owner 模型、派发、审批及自动验收。

## 4. 事务、版本与恢复

1. 在同一 SQLite 事务中读取最新 revision、核验 expectedRevision 与项目/任务事实，再追加记录。
2. 数据库复合唯一键与条件检查共同防并发。失败不追加半条记录；禁止覆盖旧版本。
3. 每次读取都核对主体归属；删除任务后的历史保留不能被当成可继续执行的计划。
4. 目标/标准变化后，旧提案显式 stale。规划结果晚到、跨项目/跨任务、角色停用或源上下文改变时拒绝保存/确认，提示重新规划。
5. 规划记录提交后可以发送“规划变化”的 UI 通知，但首片**不**发送 ready_candidate 或调用现有派发。外层事务回滚也不能发送已提交通知。
6. 重启恢复只重读草案/确认状态，不由 confirmed 自动续跑。只有后续受控执行契约通过，才可关联既有启动门禁。

## 5. 与现有 Goal 层的关系

首片不迁移或同步两套 Goal 数据。项目 Owner 目标权威暂落项目内版本记录；长期 Goal 或会话 Goal 如需参与，应增加显式 projectId/taskId/planVersion 引用并定义主从关系，经映射审查后再接。

不会把一份项目计划复制成 Goal.todos 再维护另一套任务完成事实，也不将 Goal 的 phase/completed、检查点 evidence 文本或 quota 留空解释为项目验收/执行许可。

## 6. API 与 UI 接入顺序

- 服务/隔离测试 → shared 请求/响应契约 → IPC handler → preload → Jotai atoms → 现有项目概览入口。
- IPC 身份固定主进程 actor，输入不得带权限模式、授权 ID 或客户端生成的目标版本。
- UI 默认输入目标与可选约束，草案缺配置仍能保存；已确认计划展示“尚未授权”，不能把绿色确认状态标成正在执行。
- 明确继承资料/员工/工作位置的来源和缺项，不要求人手填所有 ID；权威目录适配需补 AO-02 核验。
- 不新建依赖包，遵守 SQLite 权威存储契约；新增表可重开且兼容旧库。项目/任务备份关系与删除策略须补存储测试。

## 7. BDD 清单与当前边界

- 仅目标可保存，约束/标准可空；保存/读取不创建 task、execution、grant、费用记录或模型调用。
- 项目与单任务明确区分；跨项目/不存在任务拒绝。
- 首次 revision 生成、重复/并发提交、旧 expectedRevision 冲突，不覆盖历史。
- 修改目标/标准产生新 goalVersion 并失效旧 plan；无内容变更不制造不必要目标版本。
- 数据库重开仍能读取草案；仅 confirmed 计划不会自动派发。
- 计划提案通过结构校验仍为 proposed；角色目录/目标/来源变化后拒绝。
- 人类确认只确认计划，不能创建授权或接受客户端 actor。
- 所有存储测试使用临时 `PROMA_TEST_CONFIG_DIR`，清理并验证真实配置不受影响。
