## 1. 目标与非目标

### 目标

Owner 不只是用户与员工之间的消息中介，而是围绕同一组可检查、可版本化、可追责的项目状态，负责协调判断和行动边界的责任层。

系统需要满足：

- 用户主要只对接 Owner；员工工作可监控，但用户不直接与员工对话。
- Owner 只在影响决策的状态变化后增量核对，不因页面打开或固定轮询重复消耗模型预算。
- 本地确定性状态检查与 Owner 语义判断分离。
- 每次重要判断都有来源、假设、证据、适用范围、费用状态和下一责任人。
- 用户可以看到、质疑、修正、撤回或暂停共同状态中的关键对象。
- 应用重启、费用未知、授权变化、员工问题失联时 fail closed，不伪造恢复、不重放旧请求。

### 非目标

- 本阶段不重写现有 SQLite 权威表。
- 不把派生投影当作新的权威数据源。
- 不用固定定时器替代项目理解。
- 不把模型自述、流畅回复或测试替身当作真实成果验收。
- 不在没有实时预算和费用证据时自动增加 Provider 调用。

## 2. 共同工作空间的对象模型

项目页面分为“Owner 对话”和“共同工作空间”两层。对话是表达意图、讨论取舍和提出问题的入口；共同工作空间是可检查的状态和证据入口。

共同工作空间至少包含以下对象：

| 状态域 | 主要内容 | 默认责任人 | 典型变化 |
|---|---|---|---|
| `goal` | 目标、约束、完成标准、不可接受条件 | 用户确认，Owner解释 | 用户修改目标或约束 |
| `plan` | 方案版本、假设、步骤、依赖、完成标准 | Owner | 方案生成、过期、被目标替代 |
| `authorization` | 预算、次数、期限、资料范围、模型/Runtime边界 | 用户确认，系统核验 | 过期、耗尽、撤权、费用未知 |
| `execution` | 员工、命令、执行、heartbeat、队列、终态 | Owner协调，员工执行 | queued/running/completed/failed/stale |
| `artifact` | 文件、正文、hash、版本、是否仍可读取 | 员工产出，Owner核对 | 文件变化、丢失、替换 |
| `evidence` | 来源、测试、Reviewer、浏览器检查、费用回执 | 系统收集，Owner解释 | 证据到达、失效、不完整 |
| `employee_interaction` | 员工问题、冻结上下文、讨论轮次、等待人、超时 | Owner中介，用户决定高风险事项 | pending/discussing/decided/resolved/stale |
| `external_environment` | 工作区、Git、MCP、外部资料、连接状态 | 系统发现，Owner判断影响 | fingerprint或连接状态变化 |
| `conversation` | 用户与Owner消息、Owner回复、未决问题、变更提案 | 用户与Owner | 新消息、答复、决策、撤回 |

每个域都有独立 revision、来源和完整性校验；域之间通过显式 ID 与 revision 关联，禁止按名称或“最近记录”猜测关系。

## 3. 权威事实、原始证据与派生投影

### 3.1 权威事实

继续使用现有 SQLite 表作为权威来源，包括：

- `project_owner_revisions`
- `project_owner_management_messages`
- `project_owner_management_events`
- `project_owner_planning_run_receipts`
- `project_owner_planning_run_outcomes`
- `project_owner_execution_grants`
- `project_owner_execution_commands`
- `agent_executions`
- `project_owner_employee_interactions`
- 交付、Reviewer、文件和费用相关账本

这些记录追加保存，不用新的摘要覆盖原事实。

### 3.2 原始证据

每次模型、员工、验证器或外部系统产生的原始证据必须保留：

- Provider/Runtime 原始回执、request ID、response ID；
- response hash、request hash、token usage、费用状态；
- 文件内容 hash 与读取状态；
- Reviewer 原文和逐项标准；
- 浏览器验证命令、结果和适用范围；
- 失败原文与安全脱敏后的用户说明。

费用未知不能被本地估价覆盖，原始证据不能被后续 Owner 摘要替代。

### 3.3 可重建状态投影

新增一个可重建的派生投影，例如 `project_owner_state_projections`，不取代权威表：

```text
project_id
subject_key
goal_revision
plan_revision
authorization_revision
execution_revision
artifact_revision
evidence_revision
employee_interaction_revision
conversation_revision
external_environment_revision
dirty_domains_json
next_required_actor
next_required_action
state_hash
last_reconciled_at
projection_version
```

配置策略优先使用版本化 JSON；已有项目事实与费用继续在 SQLite。投影存于同库是建议而非已批准迁移，属于可删除重建索引。原始大文件/SDK JSONL留在原存储，投影仅保存引用和摘要。

投影用途：

- 快速判断项目是否发生影响 Owner 判断的变化；
- 记录哪些域需要增量 reconcile；
- 让 UI 快速展示当前状态和下一责任人；
- 应用重启后从权威表重建；
- 投影损坏或版本升级时 fail closed 并重建，不伪造状态。

投影 hash 只包含影响决策的字段，不包含 rowid、UI展开状态、重复读取次数或无意义 heartbeat 波动。

## 4. Dirty signal 与事件分类

现有 `project_owner_management_events` 继续作为事件入口，但事件需要明确 `domain`、主体和来源身份：

```text
id
projectId
taskId?
domain
kind
sourceId
sourceRevision
createdAt
consumedAt
payloadHash
```

推荐映射：

| 事件 | 域 | 是否默认需要模型 |
|---|---|---|
| `goal_saved` | `goal` | 是，重新核对目标影响 |
| `plan_confirmed` | `plan` | 否，先做本地安排核验 |
| `delegation_confirmed` | `authorization` | 否，先做额度/期限核验 |
| `execution_observed` | `execution` | 否，先更新进度 |
| `execution_completed` | `execution/evidence` | 视是否有成果判断而定 |
| `artifact_changed` | `artifact/evidence` | 视完成标准而定 |
| `employee_interaction_created` | `employee_interaction` | 视问题类型而定 |
| `employee_interaction_timeout` | `employee_interaction/execution` | 否，先确定性收尾 |
| `message_received` | `conversation` | 是，若消息要求判断 |
| `grant_expired` | `authorization` | 否，本地暂停 |
| `cost_reconciled` | `authorization/evidence` | 否，先更新账本 |
| `workspace_changed` | `external_environment` | 视 fingerprint 影响而定 |

重复事件必须以来源 ID、source revision 和 payload hash 幂等处理；晚到事件不能覆盖更新版本。

### 4.1 无变化不调用模型，但时间边界也是事件

“无更新”指决策相关的语义状态没有变化，不表示停止所有本地检查。授权到期、等待截止、租约失效、心跳从健康跨越到失联、外部数据新鲜度到期，都是由时间触发的新状态。

建议用最近 deadline 定时唤醒，并保留低频本地补偿扫描，覆盖 watcher 丢事件、崩溃和跨进程写入。heartbeat 每次更新不触发模型，只有健康等级跨界才产生状态事件。时间戳不能直接进入语义 hash，否则会永久变脏。

### 4.2 并发、丢事件和重建

- 能在同库提交的变更与事件/dirty标记在同一事务提交，提交后才发通知；通知丢失由未消费事件补偿。
- 外部文件事件只能作为线索，先重读受授权路径的hash/来源，再认定变化；不默认递归监控整个工作区，更不自动抓取全部MCP数据。
- `projection_version`是投影算法版本；源向量是各权威对象ID+revision+hash，不能虚构现有表没有的全局revision。首版允许使用受限查询聚合的摘要，后续再引入事务修订号。
- 单项目/主体使用有租期的处理认领；投影提交采用expected revision/CAS。运行中又有更新时保留新dirty事件，不能被旧任务“清空全部dirty”。
- 模型调用键包含主体、受影响域、来源向量、策略版本和用途；同键已有发送/未知记录不能自动再发。模型返回时重验来源，过时结果保留但不直接执行。
- 错误次数、退避截止和故障指纹持久化；应用重启不清零。无需模型即可生成阻塞说明，不能一边声称暂停一边悄悄重试。

## 5. 三层处理循环

### 5.1 本地确定性 reconcile

任何唤醒先执行本地检查，不消耗模型预算：

- 消费并校验待处理事件；
- 重算授权期限、预算、请求次数和未知费用占额；
- 检查 queued/running/failed/stale 的命令与 execution 绑定；
- 检查 heartbeat、员工问题超时和应用重启遗留；
- 检查文件 hash、Reviewer 证据与交付版本绑定；
- 检查是否存在旧目标、旧方案或旧 grant 仍被错误引用；
- 更新投影、dirty domain 和下一责任人；
- 可以直接处理的状态变化直接处理，不启动模型。

### 5.2 Owner 增量语义判断

只有以下情况才生成 Owner 管理请求：

- 用户修改目标、约束或完成标准；
- 员工结果需要业务取舍或质量判断；
- 员工问题不能在已确认范围内安全回答；
- 方案被目标、资料或证据变化实质性影响；
- 交付或 Reviewer 结果要求解释、返工或用户决定；
- 用户明确要求 Owner 重新判断。

请求只携带受影响域、当前版本和必要证据包，不重新注入整个项目历史。发送前再次核对授权、预算、来源 fingerprint 和幂等键；未知费用或能力不支持时 fail closed。

### 5.3 用户可见刷新

用户打开项目或收到通知时：

1. 读取本地最新投影；
2. 执行有界确定性 reconcile；
3. 刷新 Owner 当前关注、共同工作空间和历史；
4. 若需要语义判断，显示“Owner需要重新核对”及原因；
5. 不因为单纯打开页面自动发送模型请求。已存在的合法事件可由后台按原授权处理，但页面读取本身不制造新事件或新许可。

## 6. 员工交互契约

将员工问题视为项目状态对象，而不是临时聊天消息。字段包括：

```text
expiresAt          # 仅对“等待Owner自动答复”生效
nextRequiredActor  # owner | user | system
discussionMessageId # 讨论所属Owner消息，用于冻结上下文
executionClosePolicy
```

规则：

- 普通业务问题可由 Owner 在已确认目标和范围内回答；
- 目标、预算、资料范围、权限、系统接管和不可逆行动必须回到用户；
- 权限类交互不能由 Owner 代签；
- 讨论只更新 `discussing_user` 和冻结上下文，不扩大目标或授权；
- 应用重启不重建旧 Promise，不把旧决定投递给新会话；
- 未知费用继续保留占额，不因交互失联自动释放；
- 同一 interaction revision、request hash 和来源执行只能幂等处理一次。

### 6.1 期限与作废边界（已确认决策，2026-10-25）

**等待 Owner 自动答复有期限，等待用户决定没有期限。**

| 状态 | 含义 | 是否超时作废 |
|---|---|---|
| `pending_owner` | 尚未进入讨论，等待 Owner 自行判断或起草答复 | 是。超过期限（当前 30 分钟）后拒绝原等待、标记失联、写一次说明，不自动重试 |
| `discussing_user` | 已把问题转到用户面前，等待用户决定 | **否。** 不得因超时把用户尚未决定的事项标为失效 |
| `decided` / `delivering` | 已定案、正在回流 | 否，只按回流结果与幂等规则收尾 |

`discussing_user` 的边界来自授权本身，而不是计时器：

- Owner 管理授权的有效期到期 → 暂停后续自动推进并说明，**待决事项保留**，恢复授权后可继续；
- 员工执行授权到期或租约失效 → 按授权规则暂停或收尾，交互保留原因；
- 员工 Runtime 已确认停止 → 交互标记失联并说明真实终态。

因此“超时”只结束**自动答复**这一条路径；员工的原始提问与用户尚未做出的决定都不会被时间悄悄丢弃。

当前实现（`0.13.311`）对 `pending_owner` 与 `discussing_user` 统一套用 30 分钟期限，属于需要修正的偏差：应只对 `pending_owner` 生效。

### 6.2 问题标识与公平性

问题应新增稳定 `questionId`，不再单靠问题原文匹配；重复原文也能区分。旧数据通过显式协议版本兼容，不能给旧请求补造答案。优先级采用有限等待 + 加权公平队列，用户消息可优先但不得永久饿死员工问题；支持按任务合并问题但保留逐问题答复与来源。同一员工或交互的阻塞通知需要限流，但被合并的事项仍保留在共同工作空间，不得静默丢弃。

### 6.3 停止语义

超时首先意味着“原等待失效、请求停止”，不等于实际 Runtime 已停止。必须复用原停止/取消链，收到终态或可证明进程结束后再收尾 execution；无法确认则 command 进入 `unknown`/`needs_reconcile` 并保留占额。跨 SQLite 与内存 Promise/Runtime 的动作使用持久意图和幂等回执，不声称单个数据库事务能原子取消外部进程。

### 6.4 决策权限

用户可明确设置“需求取舍必须问我”等决策规则。首版采用显式风险/决策类型策略，不仅靠 prompt；Owner 可提出分类建议，但不能自行降低用户要求的审批等级。

## 7. Owner 预算占比与行动边界（已确认决策，2026-10-25）

### 7.1 单一占比上限

Owner 的模型开销（规划、管理、对话、员工问答、质量判断）在项目总预算内设**一个占比上限，默认 20%**：

```text
ownerModelSpendMicros + ownerModelReservedMicros <= floor(projectBudgetMicros * 20%)
```

- 超出上限即停止发起新的 Owner 模型请求，向用户说明已用量、上限、以及继续需要的增量授权；
- 提高占比或提高项目总预算都必须是用户新的明确授权修订，不能由 Owner 自动放宽；
- 未知费用继续占额，不能因结算不到而释放额度；
- 预留与实际结算共享同一本账，同一请求不能重复计费。

Owner 模型之外的执行开销（员工执行、评审、验证）继续使用项目预算的其余部分，并沿用既有逐命令账本与授权校验。

### 7.2 其余交由 Owner 自主

除以下边界外，Owner 在已确认的目标、约束、资料范围、执行授权与上述占比内**自主决定**：

- 如何拆解步骤、选择员工与评审、组织返工、安排顺序；
- 何时向用户提问、如何措辞、是否需要多轮讨论；
- 是否使用更多请求次数，只要不越过占比上限与授权有效期。

不再为员工问答、评审、规划分别设置独立的预算子桶，也不再预设讨论轮数上限。原第 7 节的分桶方案（`planning_budget` / `employee_mediation_budget` / `delivery_review_budget` / `execution_budget`）**由本节取代**，避免 Owner 因为内部记账分类被反复打断。

### 7.3 触发重新授权的情形

只有以下情形需要用户重新授权，其余不需要打扰用户：

- Owner 模型占比达到上限；
- 项目总预算耗尽；
- 目标、约束或完成标准变更；
- 资料范围、工作区或外部权限变化；
- 高危、不可逆或对外发送类动作；
- 授权到期。

## 8. 证据包与 Owner 输出

Owner 的重要回复不只保存自然语言，还应关联一个可检查的证据包：

```text
结论
受影响状态域与revision
来源事实与sourceRefs
假设
替代方案
测试/Reviewer/文件证据
适用范围
未解决问题
费用与授权状态
下一责任人
可撤回或暂停动作
```

例如本次 `acceptanceCriteria [` 失败应呈现为：

- 结论：当前方案不能继续；
- 依据：原始 Provider response hash、request ID、响应时间；
- 失败点：第三步字段结构不符合严格协议；
- 影响：没有生成可用方案，不允许派工；
- 费用：有 token usage，成本回执未知；
- 动作：不自动重试、不释放未知预留；
- 下一步：用户查看原请求并决定是否重新确认范围。

提出结论的 Owner 不应成为唯一裁判；结构验证、文件 hash、测试和独立 Reviewer 必须保持独立。

## 9. UI 结构

### Owner 对话

承担：

- 用户表达目标和约束；
- Owner 解释当前判断；
- 多轮讨论和用户决定；
- 反馈、暂停、撤回和授权确认。

### 共同工作空间

承担：

- 当前目标与方案版本；
- dirty domain 和最后 reconcile 时间；
- 下一责任人和下一动作；
- 员工只读工作记录；
- 授权、预算和未知费用；
- 证据包、Reviewer 结果和适用范围；
- 未决员工交互；
- 决策历史、撤回入口和异常恢复说明。

用户仍只通过 Owner 做决策，不需要进入员工聊天页面。

### 阶段 D0：等待与恢复止血（最高优先级）

- 先补员工等待截止、停止请求、重启遗留认领、持久退避和Owner阻塞说明；
- 覆盖Owner解析失败/额度耗尽时员工不永久假running；
- 将“等待失效”“Runtime已停”“费用已结清”三个状态分开；
- 验收：模拟无回执、格式错、停止失败和重启，确认旧Promise不恢复、unknown费用不释放、不新增付费请求。


### 阶段 A：状态域与投影

- 定义 domain、revision、state hash 和 projection schema；
- 从现有权威表构建投影；
- 覆盖目标、方案、授权、执行、证据、员工交互和对话；
- 验收：投影可删除重建，重建前后 hash 一致；不触发 Provider。

### 阶段 B：事件分类与确定性 reconcile

- 为现有事件增加 domain 和来源身份；
- 将 30 秒巡检改为“发现事件 + 更新投影 + 有界 reconcile”；
- 加入授权过期、执行遗留、交互超时、证据失效和未知费用检查；
- 验收：无 dirty domain 不生成 Owner 请求；重复/乱序事件幂等。

### 阶段 C：增量 Owner 语义调用

- 只为需要语义判断的 dirty domain 组装上下文；
- 保存 request scope、输入 hash、source revisions 和证据包；
- 调用前重新核对预算、授权、能力和费用状态；
- 验收：同一 state hash 不重复调用；状态变化只影响对应域；未知费用 fail closed。

### 阶段 D：员工交互可靠性

- 增加超时、重启收尾、Promise失联、执行收尾和预算 bucket；
- 区分未发送、已发送已结算、已发送未知费用；
- 验收：问题不会永久 pending；重启不重放旧决定；未知费用不释放。

### 阶段 E：证据包与共同工作空间 UI

- 展示当前状态、证据、预算、未决事项和下一责任人；
- 提供 Owner 反馈、暂停、撤回和核对入口；
- 员工工作记录保持只读；
- 验收：用户不用进入员工会话即可了解项目并完成必要决定。

### 阶段 F：真实端到端与互补表现

- 固定包验证无人追加用户消息时的主动推进；
- 真实 Provider、真实员工执行、真实文件交付和 Reviewer；
- 测量错误发现、撤回、证据充分性、用户负担和独立完成对比；
- 验收：任何结论都标注真实/替身边界，不用自动化率冒充人机团队效果。

### 10.1 横向验收门禁

- 安全：篡改项目/任务/执行/请求/revision、跨项目、过期grant和重复投递均拒绝；投影无法直接批准动作。
- 调度：无变化重复本地扫描的模型调用增量为0；deadline跨界只生成一次有效事件；乱序/重复/漏通知后能重建一致投影。
- 公平：持续用户消息与多个员工问题并发时，在配置等待上限内得到处理或明确暂停，不永久饿死。
- 费用：总额与bucket双重约束，unknown保留，原始usage与cost来源不篡改；不把预留当实际费用。
- 证据：文件变更后旧Reviewer结论失效；替身测试和真实Provider/真实App证据分栏标注。
- UI：用户只通过Owner完成讨论和审批；能看到当前阻塞、来源、下一责任人、停止是否确认及费用状态。

### 10.2 指标与实施边界

首轮采集：重复调用率、无变化模型调用次数、事件到可见状态的延迟、员工等待时长与饥饿数、unknown费用未核销额、停止确认率、证据覆盖率、用户必要决策次数。人机互补表现需要对照同类任务的质量/成本/时间与用户负担；不能仅以自动化率证明。

共享对象的“撤回”需要区分撤销未执行命令、停止运行任务、修订决定与补偿已发生外部副作用；不可逆动作不能承诺撤销。事实/假设/决定要分栏，AI推断不能静默变成用户确认事实。共同记忆可查看/纠正/迁移/删除，删除涉及审计保留时解释边界；其实现单列后续里程碑，不塞进第一阶段。

## 12. 设计决策

本 RFC 的核心决策是：

> Owner 不持续扫描整个项目，也不因普通页面访问调用模型。Owner 维护一个可重建的项目状态投影；只有权威状态发生影响决策的变化时，才对受影响范围进行增量核对。

这将“主动管理”定义为事件驱动、状态可解释、预算受控和证据可审查，而不是固定频率的模型调用。

### 13.2 运行时不变量（新增验收门禁）

在第 10.1 节横向门禁之外，增加一组每个场景结束后自动断言的不变量。编号为本项目自定义，表达参考其 `runtime-contract.md §7`：

| 编号 | 不变量 | 对应本项目风险 |
|---|---|---|
| OI1 | 不存在非终态但没有活的持有者的员工命令或交互：必须对应运行中的回合、队列项、未决交互或等待中的父任务 | 永久等待、假running |
| OI2 | 每个终态结果最多回传一次，且至多唤醒一次请求方 | 员工决定重复回流 |
| OI3 | 同一派工不重复下发，除非显式返工 | 重复派工、重复计费 |
| OI4 | “过期”“失联”“停止请求”永远不能被记为“完成”“已批准”或“费用已结清” | 状态伪造、未知费用被释放 |
| OI5 | 执行时实际使用的权限等于其冻结授权，不能由Owner或员工消息提升 | Owner代签、权限扩大 |
| OI6 | 每次状态变化都有事件；投影可由权威事件和事实重建 | 投影漂移 |
| OI7 | 重启后被打断的回合最多重跑一次；已对外执行的回合不重跑 | 重复发送、重复写入 |
| OI8 | 唤醒Owner只发生在终态、需要决定或停滞时，不因进度心跳唤醒 | 无变化调用模型 |
| OI10 | Owner 模型开销不超过项目预算的 20%，超限必须由用户新增授权 | 预算失控、静默扩权 |
| OI9 | 运行时拒绝必须是有类型的结果，不抛进员工回合导致半启动状态 | 半启动、残留 |

这些不变量先以 BDD 夹具断言，再进入固定包验收；替身通过不等于真实 Provider 通过。

### 13.3 重启处理细分（细化阶段 D0）

当前 D0 将重启遗留统一标为 stale / unknown 并保留占额，方向安全但较粗。参考其按停机状态分类的做法，细分为：

| 停机时状态 | 处理 |
|---|---|
| 已排队、未启动 | 按原授权正常派发，不重复创建 |
| 运行中、无子任务、**未对外执行** | 最多重跑一次，回合开头注明“检查已经做过什么”；再次被打断则失败并报告 |
| 运行中、**已对外执行**（发送、提交、推送、付款、写入外部系统） | 不重跑，直接失败并说明“已对外执行，不再重做以免做两次”；费用保持未知并占额 |
| 运行中、已派出子任务 | 进入等待，恢复时说明该回合被打断，本身不再重跑 |
| 等待用户决定 | 保持等待，重新展示待决事项，不设自动作废 |
| 等待 Owner 自动答复 | 按 13.5 的期限处理 |

“是否已对外执行”只能来自运行时活动记录与工具回执，**不得采信模型自述**；无法判定时按“已对外执行”的保守路径处理。当前尚无可靠的对外动作标签来源，落地前需先补该证据。

### 13.4 代码检查优先（细化阶段 A/B）

参考其主动巡检规则，补充四条约束：

1. 外部状态、执行结果、交付物和时间边界先用确定性代码检查；**没有新内容不启动 Owner 模型回合**，只记录“已检查”时间。
2. **读取失败不等于没有变化**：保留游标与原状态，按持久退避重试，并在 Owner 当前关注区说明故障；不得据此推进或清除 dirty。
3. Owner 可返回结构化的无事可报（如 `{"quiet": true}`）；无法解析的回答判定失败、保留原始回执，**不作为 Owner 消息展示给用户**，也不覆盖方案。这与 2026-10-25 10:08 `acceptanceCriteria [` 失败的处理一致。
4. Owner 模型开销受项目预算 20% 占比上限约束（见 7.1）；达到上限时停止发起新请求并要求增量授权。不再单独设置请求次数上限。

### 13.5 计时器与等待对象（修订第 6 节）

计时器保持少而明确，并区分等待对象：

| 等待对象 | 期限 | 到期处理 |
|---|---|---|
| 员工等待 **Owner 自动答复**（`pending_owner`） | 30 分钟（已确认） | 拒绝原等待、交互失联、写一次说明、不自动重试 |
| 员工问题已转为 **等待用户决定**（`discussing_user`） | 不因超时自动作废；仅以授权有效期和执行租约为边界 | 授权或租约到期时按授权规则暂停，并说明待决事项仍需用户处理 |
| 排队未启动 | 排队上限 | 标记未启动失败，不算已执行 |
| 运行中无进展 | 单回合活动窗口，使用单调时钟，睡眠不算停滞 | 停滞并请求停止，停止确认前保留未知费用 |

当前 `0.13.311` 对所有 `pending_owner` / `discussing_user` 交互统一使用 30 分钟期限，其中 `discussing_user` 实际属于“等待用户决定”。按 6.1 已确认决策应修订为：仅 `pending_owner` 适用 30 分钟期限；`discussing_user` 改由授权有效期和执行租约约束。**期限分离已在 `.314` 实现；重启保留与重新绑定仍需独立验证。**

### 13.6 防空转与通知限流（补充阶段 B/D）

- 连续两次续跑都没有成功的工具调用，或连续三次出现相同错误文本，判定停滞并停止续跑；没有证据的执行视为“进展未知”，既不计数也不重置。
- 同一员工或交互的阻塞通知设置限流（例如一小时内第三次后合并），避免刷屏；被合并的事项仍保留在共同工作空间，**不得静默丢弃**。
- 同一故障连续出现只通知一次，与已实现的持久退避一致。

### 13.7 阶段 F 的行为评测样板

参考其 `evals/` 体系：脚本化模型替身驱动场景 JSON → 生成行为轨迹 → 与黄金轨迹 diff → 泄露扫描 → 真实模型评审。本项目阶段 F 至少纳入以下场景：

- **用户在员工工作期间发送新消息**（参考其 `dispatch-supersede`）：新消息立即处理，原派工保留、不重复下发；用于验收公平调度。
- 员工等待 Owner 超时、等待用户决定跨越授权期限。
- 重启时分别处于未对外执行与已对外执行的回合。
- Owner 返回无法解析的方案，确认不展示、不覆盖、不重试。

评测轨迹需标注替身或真实 Provider；替身轨迹不能替代真实验收。
