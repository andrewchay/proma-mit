# 项目驾驶（Project Pilot）整体方案

**日期：** 2026-09-26　**状态：** 待确认（未开始实施）
**来源：** R01 真实试跑后的使用反馈（GLM 5.3 Flash 三轮闭环后的体感问题）
**结论先行：** 核心问题不是缺功能，而是**缺一个项目级智能角色 + 缺一个统一收口**。现有能力（员工执行链、项目链路、Proactive 调度、简报、审批）已经够用，但需要一个新的编排层把它们串起来，并把散落各处的入口收敛成两个界面。

---

## 1. 诊断：把体感问题对应到具体机制

| 你的感受 | 实际机制问题 | 证据 |
|---|---|---|
| 非常不智能，需要我不停介入找每个步骤去哪点 | 缺项目级编排角色；派发、验收、返工、应用、扩范围各自是独立入口，无人串流程 | R01 中你走了 4 处界面、点了 20+ 次；三轮执行里两轮卡在流程而非模型 |
| 不进工作区就无法驱动模型 | Agent 会话/工作区是执行前提；项目侧没有「项目为范围」的运行时 | 研发执行必须先有工作区 → worktree → session；项目本身不能自己跑 |
| 点击内容太多、部分可点部分不可点 | 交互一致性缺失：任务列表行不可点、看板卡片可点、tab 语义重叠 | R01 中你两次找不到入口（任务详情、验证区） |
| 顶部「项目 / 看板」重复 | 同一份项目数据的两种视图被做成两个平级 tab | `ProjectView.tsx`：`activeTab` 含 `projects` 与 `board`，后者是 `BoardOverview` |
| 团队交互很乱 | 团队 tab 混装了"成员/角色"与"引擎配置（渠道、工作区、Skill、MCP）"两类内容 | `AgentTeamPanel.tsx` 同时管 roster 与 runtime 配置 |
| 项目内 tab 太复杂、知识没用 | tab 按"功能模块"而非"用户任务"切分；知识域尚未产生实际价值 | 11 个 tab：任务/链路/知识/工作空间/纪要/看板/甘特/依赖/活动/风险/AI成本 |
| 工作空间绑定应该在项目配置里 | 绑定散落在项目 tab 内，未归入"配置"心智 | `ProjectWorkspacesPanel.tsx` 作为独立 tab |
| 配置太多 | 无模板、无默认值继承、无一次性初始化 | 建项目需要手工配：决策、DoD、员工、工作区、验证命令、绑定 |

**判断：** 现有系统在"执行"这一层已经可靠（R01 证明了范围、快照、验收、应用、DoD 全部按设计工作），薄弱的是**编排层与信息架构**。

---

## 2. 目标形态

### 2.1 一个角色：项目驾驶（Project Pilot）

不是"又一个 AI 员工"，而是**项目级编排角色**，职责边界明确：

| 做 | 不做 |
|---|---|
| 读懂项目权威状态（任务、阻塞、交付、DoD、决策、执行） | 不替员工写代码、不改范围、不动仓库 |
| 分诊：谁该做什么、下一步是什么、卡在哪 | 不批准交付、不做业务验收 |
| 编排：创建/拆解任务、指派员工、请求返工、提醒 | 不绕过范围/快照/DoD 闸门 |
| 汇报：用自然语言说清"现在状态 + 需要你决定什么" | 不把模型叙述当权威事实 |
| 提议：范围调整、DoD 补充、优先级变化（需你批准） | 不自动改关键决策或 DoD |

**权限模型（沿用现有哲学）：** 默认 `safe`（只读+建议）；低风险动作（创建子任务、指派、请求返工、提醒）可在你首次授权后自动执行；高风险动作（改范围、改 DoD、通过交付、外部发送、付费、应用回仓库）**每次都要你批准**。

### 2.2 两个界面：合并后的信息架构

**顶部（跨项目层）**

```
现在：项目 | 我的工作 | 看板 | 团队 | 日程管家
改为：项目（含列表/看板视图切换） | 我的工作 | 团队 | 日程管家 | 收件箱(N)
```

- 「项目」与「看板」合并：同一数据的两种视图，右上角切换「列表 / 看板」，避免两个平级 tab。
- 「收件箱」新增为一级入口：**所有需要你决定的事都汇总到这里**（权限审批、交付待验收、决策待拍板、DoD 待确认、PM agent 提议、返工请求、定时任务失败）。这是"减少点击"最关键的一步。

**项目内（单项目层）**

```
现在 11 tab → 改为 5 组：
  概览      项目状态 + AI 驾驶舱（PM agent 简报、下一步建议、需你决定的事）
  任务      列表 / 看板 / 甘特 / 依赖 四种视图切换（同一数据）
  协作      决策链 + 交付验收 + 交接（合并「决策与协作链路」「依赖」）
  记录      活动 + 会议纪要 + AI 成本（合并）
  配置      工作空间绑定 + DoD + 风险规则 + 项目级默认值
  （知识 tab：在产生实际效用前隐藏，避免空 tab 干扰；保留入口在"配置"里）
```

**团队页重做**

- 只保留「成员与角色」：谁在这个项目、角色是什么、在做什么、最近表现。
- 渠道/模型/工作区/Skill/MCP 等引擎配置**整体移到设置**，项目里只做"选择"不做"配置"。

### 2.3 配置瘦身

| 现状 | 改为 |
|---|---|
| 建项目后手工配决策、DoD、员工、工作区、验证命令 | 「一键初始化」：选 Git 仓库 → 自动建工作区绑定 + 研发员工 + 默认 DoD + 验证命令模板 + 一条初始决策 |
| 员工逐个配渠道/模型/权限 | 继承全局默认，项目级只覆盖差异；模板化角色（研发/评审/文档） |
| 空 tab 也显示（知识、纪要、风险…） | 无数据即隐藏，有数据自动出现 |
| 验证命令、范围每次手填 | 按文件类型/任务模板预填，你只需确认 |

## 3. 架构方案

### 3.1 复用现有地基（不重造）

| 已有能力 | 位置 | 复用于 |
|---|---|---|
| Proactive 调度（支持 `newSession`，可不依赖用户打开工作区） | `proactive-scheduler.ts`、`proactive-scheduler-store.ts`、`types/proactive.ts` | **PM agent 的运行载体** |
| Proactive 中心（Today/Approvals/Monitors/Schedules/Routines/Runs/Memory） | `renderer/components/proactive/` | 「收件箱」与定时简报的底座（现被 dev-gate 置为 hidden） |
| 员工派发链路（会话/worktree/回写/受限交付） | `agent-employee-service.ts` | PM agent 的"执行"出口（它只发起，不替代） |
| 项目链路（决策/交付/DoD/依赖/交接） | `project-chain*.ts` | PM agent 的"事实来源"与闸门 |
| 简报回执 + 护栏通知 | `brief-callback-server.ts`、`notifyAgentGuardrail` | PM agent 的对外汇报通道 |
| 定时扫描（本地只读） | `employee-capability-scan-scheduler.ts` | 事件/周期触发的参考实现 |

### 3.2 新增三块

**A. 项目运行时（Project Runtime）**

- 新概念：`ProjectScope` 运行时 = 项目 + 工作区绑定 + 渠道/模型默认值 + PM agent 档案，不依赖用户先开工作区。
- 用 `ProactiveSchedule(newSession: true, workspaceId=项目绑定工作区, channelId=项目默认)` 承载，prompt 由主进程构造（注入权威项目状态快照），**不让模型自行猜测状态**。
- 触发源三类：手动「推进一轮」按钮、定时（默认每日站会 + 可选每 N 小时）、事件驱动（任务完成、交付待验收、依赖阻塞、DoD 未满足、执行失败）。

**B. 分诊与编排层（Pilot Engine）**

流程固定四步，全部落审计：

1. **采集**：读权威状态（任务、执行、交付、DoD、依赖、决策、最近活动）。
2. **判断**：产出结构化「行动清单」，每条含 `action / 目标 / 理由 / 风险级别 / 需要谁的授权`。
3. **分流**：
   - 低风险且已授权 → 直接执行（创建子任务、指派员工、请求返工、提醒）。
   - 需授权 → 写入**收件箱**（一条带上下文的待办，附 PM agent 建议与理由）。
   - 只读洞察 → 写入项目概览的简报区。
4. **汇报**：生成一句话状态 + 待决定事项清单，可选推送飞书/钉钉。

**硬约束：** PM agent 的动作必须走现有服务（`updateTask`、`dispatchTaskToAgent`、`requestChanges`…），**不能直接写项目库**；所有闸门保留；它自己的动作也必须留执行记录，可回放。

**C. 统一收件箱（Inbox）**

- 收口现有分散的待办：权限请求、AskUser、交付待验收、决策待拍板、DoD 待确认、依赖交接、学习样本审核、PM agent 提议、定时任务失败。
- 统一视图：按"需要谁决定 / 紧急度 / 项目"分组；支持就地处理（一条内联完成验收、批准提议、拒绝返工），**不用跳转**。
- 这是"点击减少"的核心：一处处理完，而不是回到 4 个界面各点一遍。

### 3.3 事件驱动 vs 定时

| 触发 | 场景 | 默认 |
|---|---|---|
| 手动 | 我想知道现在什么情况 / 推一把 | 开启 |
| 事件 | 交付待验收、执行失败、依赖阻塞、DoD 未满足 | 开启（增量、低耗，只做分诊不调模型也能用） |
| 定时 | 每日站会简报 | 默认每日一次，可关；连续失败自动暂停（复用现有 `consecutiveFailures`） |

**成本控制：** 事件触发先做**确定性分诊**（不调模型，只按规则判断"是否需要人"），只有需要判断"下一步做什么"时才调模型；同一项目在 N 分钟内不重复调用。

## 4. 分期实施路线

### P0：收口与可见（约 3–5 工程日）

目标：不改执行链，先让"需要你决定的事"集中、让项目状态一眼可见。

1. 统一收件箱（先聚合已有待办源，不含 PM agent 提议）
2. 项目概览页：权威状态看板（谁在做什么、卡在哪、待你决定什么），只读
3. 顶部 tab 合并（项目+看板）、项目内 tab 从 11 组改为 5 组
4. 工作空间绑定移入「配置」；空 tab 隐藏
5. 任务列表行可点开详情（补齐交互一致性）

**验收：** R01 场景重跑一遍，统计点击数从 20+ 降到 ≤8；所有待办只在一个地方处理。

### P1：项目驾驶（约 5–8 工程日）

1. PM agent 档案与角色提示（只读+建议模式先行）
2. 项目运行时（手动「推进一轮」+ 事件触发分诊）
3. 行动清单 → 收件箱（提议需批准；低风险动作授权后自动执行）
4. 团队页重做；引擎配置移设置
5. 「一键初始化项目」向导（工作区+员工+DoD+决策）

**验收：** 新项目从零到"员工开始干活"只需一次向导；PM agent 至少能自动完成"N 个任务的下一步分诊 + 指派"，且不越权。

### P2：主动推进与学习（约 5–8 工程日）

1. 每日站会简报（应用内 + 可选飞书/钉钉）
2. 事件驱动的自动编排（交付待验收→提醒你；执行失败→分析原因并提议重派）
3. 跨项目组合视图（多项目收件箱、风险总览）
4. 基于历史的效果反馈（哪些提议被采纳、哪些员工在哪类任务上返工多）→ 调整默认策略

## 5. 与现有约束的对齐（必须遵守）

- **不进工作区也能跑**：靠 `ProactiveSchedule(newSession)` 在项目绑定的工作区里创建会话；仍需工作区绑定存在（Git 执行必须落在真实仓库）。
- **不伪造成功**：PM agent 的所有结论必须引用权威 ID（任务/执行/交付 ID），禁止把模型叙述当状态。
- **权限不放松**：PM agent 默认 `safe`；提升权限必须你显式授权；高风险动作逐次批准。
- **闸门不绕过**：范围、快照、验收、DoD、应用校验全部保留；PM agent 只能"发起"，不能"批准"。
- **审计不缺失**：PM agent 每次运行的输入快照、行动清单、执行结果、你的决定全部落库可回放。
- **不夸大**：收件箱聚合与 tab 重构属确定性改造，可直接验收；"主动推进质量"依赖模型能力，需按 R01 方式真机试跑后才算验收。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| PM agent 幻觉式"推进"（把没做的事说成做了） | 结论必须绑定权威 ID + 状态字段；无依据时输出"状态不足，需要你确认" |
| 审批疲劳（提议太多） | 分级：只把"必须你决定"的进收件箱；同类问题聚合；每项目每小时最多 N 条 |
| 定时调用成本失控 | 事件触发先确定性分诊；失败自动暂停；单项目节流；预算上限 |
| 权限边界被逐步放宽 | PM agent 权限单独列出并审计；任何提升都要你确认，不随项目自动升级 |
| 大改 UI 引发回归 | tab 合并只做视图层重组，不动数据与 IPC；每步保留旧入口直到新入口验收 |

## 7. 需要你拍板的三个问题

1. **PM agent 的角色定位**：是"项目里的一个 AI 员工"（可在团队页看到、可指派），还是"系统级驾驶舱"（不在员工列表、作为项目能力存在）？我建议后者——它不是执行者，而是编排者。
2. **收件箱的入口**：加在顶部一级 tab（我更推荐），还是并入现有 Proactive Center 直接放开 hidden 门禁？
3. **P0 优先还是 P1 先行**：P0 见效快（点击减少、待办集中），P1 才是"智能"本身。建议 P0 先做，因为 P1 的提议也要有地方收。
