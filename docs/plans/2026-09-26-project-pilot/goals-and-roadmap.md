## 1. 北极星目标

用户只需说明项目目标、确认必要范围及授权，系统在应用运行期间主动组织适当角色的 Agent 工作，持续跟进结果、安排技术评审、处理依赖和有限返工；仅在缺失信息、关键业务决定、超范围或最终验收等确需人工的节点主动沟通。用户答复后，无需再寻找入口或点击“继续推进”。

**验收重点是减少人工调度，不是单纯减少点击。**

- 智能管理是主线；信息架构、收件箱、默认值继承是支撑它的产品能力。
- 不进入项目/工作区/会话页面也能运行；仍允许后台自动创建有正确范围和权限的执行会话。
- 本地应用退出、机器休眠时不承诺持续运行；恢复后对账并按有效授权继续。云端常驻是独立范围。
- 研发执行需要真实 Git 仓库；项目规划、分诊、沟通本身不应以绑定代码仓库为前提。
- 首个闭环限定到经授权的任务类型与 Runtime，不宣称全部项目均可自治。

## 2. 项目管理者的产品形态

Pilot 在产品上是可直接交流的“项目管理者”，在架构上是系统级编排能力，不是另一名普通执行员工，不进入员工指派列表，也不取代员工执行器。

项目概览提供持久的管理者交流入口：

- 用户可以直接说目标、调整优先级、回答追问、要求暂停或解释当前状态。
- Pilot 展示“正在推进什么、为什么这样分工、在等谁、需要你决定什么”。
- 对话必须绑定 projectId 与权威任务/交付/审批 ID，不能把聊天内容自动变成已生效决策。
- 明确批准的指令经过受控命令落到项目服务；存在歧义或超授权时先澄清。
- 实际执行会话是可查看的证据入口，不是用户必须进入的驾驶入口。

### 模型与确定性服务各负责什么

| 部分 | 职责 |
|---|---|
| 确定性服务 | 读取事实、依赖/readiness、权限、预算、去重、状态迁移、版本与有效性校验 |
| 模型 | 理解目标、提出任务拆解、选择适当角色、分析失败、提出调整计划、向用户解释和追问 |
| 受控命令层 | 校验结构化计划，执行授权范围内的动作；拒绝过期、重复、越权命令 |
| 员工执行器 | 在正确工作区/隔离环境中执行任务并提交证据 |
| 人工 | 必要业务决定、授权变化、最终验收及应用等保留审批 |

模型不只是简报改写器，也不持有直接修改项目数据库或自我授权的权限。

## 3. 最小主动推进闭环

```text
用户说明目标 / 项目事件 / 恢复对账
  → 采集权威项目快照
  → 确定性识别可执行/阻塞/待审阅事项
  → 必要时调用模型生成结构化计划与角色选择
  → 校验授权、预算、依赖、快照版本、幂等键
  → 派发执行者 / 安排技术评审 / 有限返工
  → 监听结果并重新对账，继续下一步
  → 仅必要事项进入收件箱并主动通知
  → 用户答复 → 校验请求仍有效 → 自动恢复对应工作链
```

### 必须补上的连接

1. 任务、交付、交接、决策、审批结果形成项目级事件入口；不是只监听当前 Task 的 assignee 变化。
2. 按项目串行对账，事件合并但不能丢失安全审批；结合持久化游标或可重建事实防漏事件。
3. 依赖未满足是 waiting，不是普通执行失败；解除后唤醒下游，不要求用户重新指派。
4. 技术 Reviewer 产出审阅证据，不等于人工业务验收。技术评审失败在授权次数内返工，再自动送审。
5. 审批记录关联待执行命令和 continuation；批准是恢复触发点，不是再点一次“运行”的前置操作。
6. scope、projectId、执行 workspace、资料授权联合校验；不得静默回落到错误的全局工作区。
7. 重复事件、重复批准、晚到旧交付、重启、取消必须有明确状态与幂等语义。

## 4. 安全与自主性：不是全自动，也不是事事点击

初始未启用托管时仅建议。用户显式开启并确认授权契约后，可执行下面的受限推进。**本次文档修订不等于授予这些权限，也不修改现有 permissionMode。**

| 动作 | 建议处理 |
|---|---|
| 读取状态、检测阻塞、生成计划 | 项目可见范围内执行；模型调用受预算约束 |
| 从已授权目标创建任务、选择白名单员工、派发、安排技术评审 | 在已批准范围、工作区、模型、并发与预算内自动执行 |
| 失败重试、技术评审返工 | 受单任务/单项目次数及成本上限约束；同原因反复失败即升级人工 |
| 改目标/扩大文件范围/改 DoD/增加预算或权限 | 提议并请求明确批准，不自动生效 |
| 业务验收、应用回仓库、发布、外部发送、购买等 | 保留对应人工确认；通知渠道可独立授权，不能将通知授权扩展为任意外发 |
| 暂停/撤权/预算耗尽 | 阻止新派发；明确在途执行停止或仅采集收尾的规则，并在开始运行前告知用户 |

模型 API 费用计入事先批准的运行预算，不把每次调用都当成另一次购买审批；没有预算授权则不能开始付费自主运行。调用金额未知不能当作 0，需要按用量上限或保守预留控制。

**现有实现边界：** Proactive 目标只允许 proma/ai-sdk 与 safe/plan；普通员工存在旧 bypass 路径。不能为追求自治直接放宽这些限制。优先复用 headless 执行与服务命令，通过单独验证的 Pilot 授权契约衔接；旧 bypass 员工默认不进入首版托管角色池。

## 5. 工作区与低配置开通

用户面对的是“项目要在哪里工作”，不应分别理解三份配置：项目资料绑定、员工适用工作区、任务执行工作区。

- 默认值继承全局有效渠道/模型与可用角色模板；项目只覆盖差异并展示最终生效值。
- 代码任务选择仓库后，预检并生成工作区/角色/验证模板候选；不自动伪造“已拍板决策”。
- 项目规划、非代码任务使用隔离的管理上下文；若复用现有 runner 仍需内部 workspace，应由系统管理，不要求用户为了讨论先建 Git 仓库。
- 资料访问通过现有 project scope 与绑定校验，不把工作区绑定扩展为任意文件共享。
- 验证命令由模板/仓库信息提出，不盲目执行未知命令；缺有效渠道、模型或权限时集中提示缺项。
- 用户确认目标、执行位置、预算、范围、授权，其他配置渐进展开。

## 6. 信息架构与入口

顶部：`项目（列表/状态总览） | 我的工作 | 收件箱(N) | 团队 | 日程管家`。

注意：当前 BoardOverview 是项目状态统计卡片，不是项目级可拖拽看板；合并入口时保留现有统计语义，并新增可下钻能力，不误称现有拖拽能力。

项目内稳定五组：

| 分组 | 内容 |
|---|---|
| 概览 | 管理者交流、项目摘要、并行任务汇总、当前里程碑、待我决定 |
| 任务 | 列表/看板/甘特/依赖；统一任务详情、执行证据及流程 |
| 协作 | 决策、交付审阅、交接；依赖只引用任务权威关系 |
| 记录 | 活动、会议纪要、执行记录和成本统计 |
| 配置 | 工作区、DoD 定义、角色与默认值、风险规则、知识授权 |

- 我的工作回答“我要执行什么”，收件箱回答“谁在等我决定”，概览回答“项目怎么样”。
- 项目显示多任务汇总，任务显示适用的流程与返工轮次；二者同源但不共用线性状态机。
- 已启用但无数据显示空状态，不动态隐藏主导航。知识绑定已有实际授权作用，可移入配置，不删除能力或权限语义。
- 团队把成员/角色/可用性与引擎编辑分开；常用角色选择在项目可完成，高级配置进入设置。
- 工作区绑定移到配置；任务行可开详情、验证区可发现、范围更新后可重新冻结交付。

### 收件箱契约

首批：权限/AskUser、交付待人工验收、项目决策、Pilot 的必要提问与超授权请求。

原服务持有权威状态，收件箱只统一投影和受控动作入口。每项关联 sourceType/sourceId、projectId/taskId、版本、处理者、有效期、状态和可执行动作。执行前重校验，多入口同步，重复动作幂等。

简单问题内联处理；交付审阅可展开抽屉检查 diff、验证、范围和版本，不能为了少点击省略必要证据。处理中不丢上下文，源服务确认成功后才显示完成。

系统主动通知定位到项目事项，答复后恢复相应 continuation。现有内存中的工具审批若重启后失效，须标为失效并重新对账，不伪造恢复或重放旧授权。

## 7. 分期与完成标准

### P0：最小受控主动管理纵向切片（第一交付）

同时提供后台闭环与最小可用入口，不以全面 UI 重构为前置条件。

- 一个试验项目、至少执行者与技术评审者两种角色。
- 目标输入/必要追问、项目上下文、显式托管授权、受限模型规划。
- 事件→判断→派发→技术评审→有限返工→待人工验收。
- 最小顶部收件箱、主动通知、答复后续跑。
- 基础幂等、版本检查、预算/重试限额、暂停和项目隔离必须同批交付，不能留到“以后做安全”。
- 最小崩溃安全同属 P0：派发/审批落地前后中断，重启后先对账；无法确认执行结果或授权有效性时默认暂停，不重复派发，不恢复失效授权。对应 A09a 必须在 G1 通过；完整故障矩阵留 P1。
- 首次真实试跑必须先通过 G0/G1，并取得用户针对 fixture、模型、预算和授权的单独确认。
- 同批修复任务行/Review 可达等直接卡点；项目+总览合并、绑定移配置可并行，不阻塞后台试验。

**P0 验收：** 固定构建下，用户确认目标与授权后离开项目/会话页；系统自动安排角色和至少一次技术评审返工，并正确发出一个必要人工请求；用户答复后系统自动继续到最终人工验收前。期间不要求用户重派、催办、找会话。未验收前不默认给其他项目开启。

### P1：可靠运行与日常可用

- 覆盖重启、丢事件、重复审批、晚到结果、多任务依赖唤醒、多项目隔离及在途撤权。
- 统一审批生命周期和项目概览，完善五组导航、团队拆分与配置默认值继承。
- 对应用存活的约定观察窗口记录推进/停等/恢复、人工介入、费用和失败；不能只验收一次 run success。
- 补非代码项目和其他 Runtime 组合，逐项放行，不外推 P0 结论。

### P2：扩展与策略优化

- 定时简报、授权外部通知、跨项目资源分配、长期质量统计。
- 基于采纳/返工结果提出策略调整；学习不自动提升权限。
- 云端常驻另行立项，明确凭据、租户隔离、预算和运维边界。

不沿用旧方案 3–5/5–8 工程日估算；待 P0 命令与授权契约、可运行 fixture、测试范围确定后再估时。

## 8. 核心指标

1. 人工流程推动次数：重新指派、点继续、催办、寻找下一入口，首个标准场景目标为 0。
2. 必要人工决定次数：按场景预先定义，与流程推动分开统计；不能把必要批准“优化掉”。
3. 自动推进覆盖：预先标注可自主推进的步骤中，系统正确完成的比例。
4. 停等/恢复正确性：该停时停、批准后继续、拒绝后不执行、撤权后无新派发。
5. 真实质量：权威交付、技术评审、验证、人工验收各自留证；不以文本自述替代。
6. 成本与恢复：模型用量/费用、返工轮数、重复动作数、对账耗时；未知保持 unknown。
7. 点击数/首次用户可发现性：作为次级 UX 指标重新建立基线；旧“20+ 次”无逐步计量，不计算精确改善率。

- 自动技术评审与最终人工验收的边界；暂停时在途任务的处置。
