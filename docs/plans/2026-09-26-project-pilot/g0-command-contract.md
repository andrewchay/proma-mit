# Project Pilot G0 命令与预算契约（待审查草案）

日期：2026-09-26。本文把首版真实派发前必须满足的权威边界写成可实现、可测试的契约；它不是运行授权。当前 `project-pilot-policy.ts` 只保存 `paused` 草案，`assertPilotPolicyActive()` 始终拒绝，本文不改变这一事实。

## 为什么要先定这个契约

项目管理者需要能自主派发、评审和有限返工，但现有普通 AI 员工路径可以独立创建执行，`pilot_command_id` 和 `pilot_command_links` 只证明执行来源的声明与关联，不能证明用户授权、预算额度或来源版本。现有 token usage JSONL 在模型返回后记录用量；缺费用或价格时可能为 0，不能用它做派发前的权威预算余额。若先开放派发，再补这些控制，暂停、重启或重复事件都可能把同一动作执行两次。

## 权威数据与边界

- 项目、任务、执行及活动继续以 `paa.db` 为权威；项目文件和工作区资料不复制到命令记录。
- 当前 JSON 策略仅为配置草案。未来真实运行授权须在项目 SQLite 中形成独立的版本化 grant，至少冻结项目、有效期、目标范围、工作区、执行/评审员工、渠道/模型、最大费用、最多执行与返工次数。任何配置草案变更都不能静默扩大现有 grant。
- grant、命令、费用预留、执行归属和排队状态须在同一 SQLite 事务内写入。暂停必须在该事务中先将 grant 改为不可派发，再条件取消尚未启动的 Pilot 队列；运行中执行按用户逐项确认的选择处理。现有 JSON 草案暂停/确认实现只是过渡性内部切片，不能替代这条活动授权事务；当前暂停预览和条件取消仍只凭归属标记与关联表，启用前必须改为核验账本命令及 grant。
- 费用金额使用整数 micro-USD，写入预算预留和实际结算。模型单次最大费用未知或价格缺失时拒绝派发，不能把未知按零计算。结算声明必须绑定 execution/session/channel/model 并保存来源类型；缺最终用量、账本金额与证据金额不一致时保留预留并停等人工核查。结构化字段不等于可信回执，生产入口还必须由受信采集器核验原始 Provider 回执或不可变价格快照，并拒绝同一回执重放。
- `pilot_command_id` 与关联表是来源线索。只有受控命令账本中状态、来源版本、授权版本和预留均核验后，才允许它成为启动许可。普通员工执行保持无 Pilot 归属，不能被 Pilot 暂停批量取消。

## 命令记录的最小字段

| 字段 | 约束与用途 |
|---|---|
| `commandId`, `projectId`, `grantId`, `grantRevision` | 不可改写的身份；跨项目或旧授权不得复用 |
| `idempotencyKey` | 由项目、源类型/ID/版本、动作和目标组成；同键同内容返回同一命令，同键异内容拒绝 |
| `sourceType`, `sourceId`, `sourceVersion`, `sourceHash` | 执行前重读权威源；旧版本、过期审批和晚到结果失效 |
| `taskId`, `employeeId`, `role`, `workspaceId`, `channelId`, `modelId` | 与 grant 和当前任务/员工绑定一致；首版执行与技术评审不得同人，旧 bypass 路径不在白名单 |
| `reservedCostMicros`, `maxRunCostMicros`, `runOrdinal`, `reworkOrdinal` | 同事务检查剩余额度及次数；未知成本不得占用零额度 |
| `executionId`, `state`, `createdAt`, `updatedAt` | 一命令最多一个执行；`reserved → queued → running → settled/failed/cancelled/needs_reconcile` 单向迁移并留审计 |

## 派发与恢复顺序

1. 用户明确确认目标、范围、配置、预算和有效期后，独立生成 grant；具体 fixture、模型、费用上限与调用上限在激活前冻结。默认没有 grant。
2. 收到候选动作时，先重读项目、任务/依赖、来源版本、grant、员工、工作区、模型和权限。任何未知或不一致都返回阻塞原因，不创建执行。
3. 在 SQLite 事务中比较 grant 版本与状态、去重键、未结算预留加已结算费用、次数上限；预留金额按“剩余授权费用 ÷ 剩余执行次数”向上取整，由账本派生而不接受调用方金额；写入命令和预算预留，再创建带命令归属的 `queued` 执行。重复调用只读取原结果，不再预留或新建执行。Runtime 启用前还必须把该额度作为本次执行的硬上限。
4. 启动前再次核验命令、grant、来源和执行归属，并以条件更新认领队列。超过有效期、预算不足、暂停或关联不明时不启动模型。队列认领与启动 Runtime 之间必须再次防止暂停、取消或授权过期穿透；当前普通员工入口在核验后仍可能先创建 session/worktree，未实现原子认领和临启动复核。Runtime 创建成功与否都必须可对账，不能靠内存标志判定。
5. 重启先扫描 `reserved/queued/running/needs_reconcile`：无执行的预留要判断是否安全重试，未知 Runtime 结果保留费用并停等；有执行但缺命令归属绝不补造授权；已终结命令不重派。审批恢复重新核验源版本和 grant，不重放旧许可。
6. 用量结算与执行结果分别入账；结算前核验终结执行、命令/员工/来源关联、session、渠道、模型、证据时间和金额。费用明细缺失、超过单次上限、结果无法确认时停止后续派发并报告。人工业务验收仍为独立门禁。

## 必须通过的 G1 确定性场景

- 同一事件并发/重复到达，只得到一个命令、一次预留、一个执行；同键不同内容拒绝。
- 改任务版本、跨项目任务/工作区/员工、失效授权、旧审批、依赖未解除或超返工次数均不创建执行。
- 预算恰好耗尽、价格未知、费用晚到与超限均停止后续派发；未知费用不被当成零。
- 派发前、命令写入后、队列认领后、Runtime 返回前、结算前分别模拟崩溃；恢复不重复启动，不能确定时停等人工。
- 用户确认暂停的快照变化需重确认；确认后同事务封闭新派发并取消仅属该 grant 的未启动队列；运行中逐项处理且报告停止是否验证。
- 在应用仍运行但项目页和会话页均未挂载时，后台事件和审批恢复能继续；真实模型与多角色闭环另属 G2。

## 当前实现与下一步

已具备只读配置预检、历史候选意图、执行归属、持久命令关联、内部暂停确认和保守的排队恢复。项目概览控制面可保存始终 paused 的策略草案，只列安全研发员工并要求共同 Git 工作区、同渠道/模型及明确额度；主进程仍会重新预检，UI 筛选不构成授权。发行必须先返回冻结影响面，再由用户明确确认；确认时在策略文件锁内重读精确 revision 与员工就绪状态，再在 SQLite 事务中幂等写入活动 grant，已有活动记录须逐字段匹配。暂停也先展示预留、排队和运行中影响面，运行中逐项选择后同事务撤权、释放预留并条件取消未启动队列。以上 IPC/UI 都不创建命令或调用模型。预算预留、排队和启动记录核验会持有同一策略文件锁，并在 SQLite 事务中逐字段核对 grant，避免策略更新后提交旧命令。内部 `reserveAndQueuePilotCommand()` 已把账本派生的预留、命令转入 queued、排队 execution 和来源关联放在同一 SQLite 事务并支持失败回滚，但没有生产调用方。内部结算已拒绝裸费用，保存绑定 execution/session/channel/model 的 Provider 声明、带价格来源的估算或显式未知证据；Provider 回执键有跨命令唯一约束，未知或超预留会暂停 grant，恢复对账会拒绝缺证据、缺防重放键、unknown 冒充 settled 以及证据金额与账本不一致。当前 Provider 回执/价格来源仍由调用方声明，尚无受信采集或原始记录核验，派生预留也尚未作为 Runtime 单次硬上限，因此不能作为生产费用门禁。当前仍没有通用释放、真实用量接线、真实停止器、临启动原子认领或完整故障注入矩阵；Runtime 启动继续被硬门禁阻断。只读重启对账不自动重派，`request_stop` 只持久记录为待核验，不能宣称进程已终止。下一步先接受信用量/价格来源和释放规则，再接受控派发、临启动竞态防护和故障注入。G0 只有在具体 fixture、授权参数、命令/预算/存储契约完成评审后才可标通过；目前仍未通过。
