## 1. 要保护的对象

1. **验证配置**（`PinnedVerifierConfig`）：argv、允许退出码、超时、最少测试数。改动它等于改变“什么算通过”。
2. **Goal 的门禁绑定**：Goal 创建时记录的 `completionGate`（仓库根、验证配置）。它应只能在创建时写入，之后不可由模型或普通消息改写。
3. **验证回执**（`completionVerification`）：仅主进程写入，记录一次固定基线验证事实。

## 2. 当前已知的结构性缺口（必须先决定）

**缺口 A：Goal 存储文件本身可被同用户进程改写。** Goal 数据位于 `~/.gravitas/`，而 Bash 工具以同一用户身份运行，可以直接改写 JSON。现有 `goal-store` 没有签名或哈希校验，这一风险已在第三批契约中记为“本机私有文件信任”限制。

**缺口 B：测试文件可由 Agent 修改后提交。** 固定基线只保证“测的是已提交内容”，并不保证“测试本身未被削弱”。Agent 可以删除失败用例、改写断言，并提交，然后门禁通过。这是**比文件权限更根本的问题**，必须由门禁配置的一部分解决，例如：

- (a) 验证配置记录一组受保护路径及其在批准基线中的哈希；完成时若这些路径内容与基线不一致，则拒绝；
- (b) 完成门禁只接受在“批准基线”之后仅修改非测试路径的提交；
- (c) 接受风险，仅在回执中列出测试文件相对基线的变更，由人工复核。

在 (a)–(c) 中选定之前，固定基线门禁只能证明“提交内容通过了这些测试”，不能证明“测试没有被削弱”。

## 3. 存储布局（建议）

```
~/.gravitas/verifiers/                  目录 0700，仅主进程读写
  <verifierId>.json                     0600；内容：版本、argv、expectedExitCodes、timeoutMs、minimumTests、protectedPaths[{path, sha256}]、createdAt、revision
  audit.jsonl                           追加写；每行含上一行的 sha256，形成哈希链
```

- 配置不放在工作区、worktree 或 Goal JSON 内；Goal 只保存 `verifierId`、`revision` 与整个配置的 `sha256`。
- 完成时主进程按 `verifierId` 读取配置，核对 `sha256` 与 Goal 记录一致，不一致则拒绝并要求新建 Goal。
- 哈希只用于检测意外损坏与普通改动，**不是签名**：拥有同等本地权限的进程可以同时改写配置与哈希。

## 4. 写入权限

| 操作 | 谁可以执行 | 途径 |
|---|---|---|
| 新建 / 修改 / 撤销验证配置 | 仅用户 | 设置界面 → 主进程 IPC；显示完整 argv、仓库根与受保护路径后二次确认 |
| 创建 Goal 并绑定门禁 | 用户（UI/IPC） | 与上一行相同的校验；Agent 工具不提供该能力 |
| 读取验证配置摘要（id、revision、sha256） | Agent 只读工具 | 不返回完整 argv 以外的敏感信息；不返回路径内容 |
| 写入验证回执 | 仅主进程 | 完成门禁内部 |
| 直接写文件 | 无人 | 目录权限 0700；Write/Edit 工具对 `~/.gravitas/verifiers/` 路径拒绝 |

## 5. 必须诚实说明的限制

1. **同用户 Bash 无法被文件权限阻止。** Agent 可以运行 `cat`、`sed`、`python` 直接修改这些文件。路径拒绝只能约束 Write/Edit 工具，不能约束 Bash。
2. 因此，真正的隔离需要以下之一：
   - (i) 把 Bash 的可写范围限制在工作区（例如沙箱或 `sandbox-exec`），并拒绝对 `~/.gravitas` 的任何引用；
   - (ii) 将签名密钥放入 macOS 钥匙串，并让 Agent 进程无法读取该项（需要 ACL 验证）；
   - (iii) 验证器以独立 OS 用户运行（复杂度高，超出当前范围）。
3. Goal 存储目前无签名，Goal 内的门禁绑定同样只是“本机私有文件信任”。
