# 文件任务委派与人工 Review：测试与真实验收方案

状态：待实施。日期：2026-09-25 GMT+8。关联：[实施方案](implementation-plan.md) · [台账](ledger.md)。

## 1. 测试目标与证据等级

验证完整路径：文件／已有任务 → 显式派发 → 隔离修改 → 冻结交付 → 人工审阅 → 返工 → 再验收 → 确认应用 → DoD 完成。

| 等级 | 内容 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| L1 | 纯函数／状态／权限契约 | 路由、版本和拒绝逻辑 | 模型能完成任务 |
| L2 | 临时 SQLite＋真实 Git＋确定性运行器 | 隔离、快照、派发、恢复可复现 | 真实 Runtime 审批及代码质量 |
| L3 | Electron 实际 UI＋测试运行器 | 用户入口和状态展示可操作 | 真实 Provider 可用 |
| L4 | Electron＋真实 Runtime／Provider＋人工 Review | 特定组合的真实任务闭环 | 所有模型、所有仓库、长期无人值守 |

上一轮已有研发测试为 L1／L2：7＋5＋15＝27 项通过；不是本方案新增功能的测试结果。

## 2. 隔离、费用和测试数据

### 2.1 自动测试隔离

- 一切会创建工作区、会话、数据库或配置的测试，在导入业务模块前设置 `PROMA_TEST_CONFIG_DIR=mkdtemp(...)`；关闭计时器／数据库后删除临时目录并恢复环境变量。
- 每个测试文件独立 Bun 进程；全量使用 `bun run test`。
- Git fixture 使用临时仓库、临时 user.name／user.email，不修改全局 Git 配置；设置非交互模式。
- 测试前后只记录真实 `~/.gravitas/agent-workspaces/` 的目录名清单，确认无新增；不读取用户会话内容。若前后变化来自并行使用，人工归因，不能自动删除。
- 故障注入必须在临时目录；禁止对真实项目 kill／断电／reset 模拟崩溃。
- 不新增常驻服务、不把测试 fixture 链接进真实个人工作区。

### 2.2 真机与模型试跑

- 先验证打包应用是否实际支持所选测试配置隔离；不把单元测试环境变量支持等同于打包运行支持。若不支持，先补隔离启动方式或使用用户认可的独立测试环境，不直接运行。
- Runtime／channelId／modelId／应用构建号明确记录；从应用安全配置使用凭据，不复制到 fixture／文档／日志。
- 真实调用前确认费用上限和工具授权；可建议每样例 20,000 token、15 分钟为初始护栏，但必须验证 Runtime 计量与取消能力，不能声称这就是可靠货币硬上限。
- 最多两次模型尝试／样例，失败仍留档；需要增加预算时再确认。不无限自动重试。
- 不发送邮件、外部任务同步、PR、push；测试项目必须关闭外部同步。
- 没有网络／渠道／预算授权时记 `BLOCKED`，不是 PASS，也不伪造模型输出。

## 4. 可执行样例设计

### 4.1 Fixture A：代码修复

临时 Git 仓库创建 `src/format-minutes.ts`、`src/format-minutes.test.ts`、`docs/usage.md`，使用无第三方运行依赖的 Bun 测试。

已提交基线函数：

```typescript
export function formatMinutes(totalMinutes: number): string {
  const hours = Math.floor(totalMinutes / 60)
  const minutes = totalMinutes % 60
  return `${hours}:${minutes}`
}
```

任务正文：

> 修复 `formatMinutes` 的分钟部分未补零问题。期望 0→0:00、9→0:09、60→1:00、65→1:05。允许修改此模块、相邻测试和 docs/usage.md；不要改其他文件。增加覆盖这四个输入的行为测试，运行指定 bun test，并说明改动和未验证事项。

返工意见：

> 补上输入约束：负数、非整数及 NaN 均抛 RangeError；补对应测试，在 docs/usage.md 写明约束。保留第一轮功能，不重建任务或仓库。

验证命令：`bun test src/format-minutes.test.ts`。确认后的命令仅在隔离 worktree 执行。真实验收还需人工检查测试并独立核对输出，不能仅信员工写的断言。

### 4.2 Fixture B：Markdown 修改

预置 `docs/usage.md`，含一段过时配置示例和 `## 保留章节`。用户任务：修改指定配置说明、修正示例，并明确禁止修改保留章节；人工标准是语义准确、保留章节字节不变、无其他文件差异。返工：增加一个故障排查示例。

这里不要求“测试命令通过”来伪装文档质量；记录人工逐条核对依据。可用 hash 验证保护章节未变，但不能据此证明文字语义正确。

## 5. L4 真实验收脚本

### R01：代码修复 → 返工 → 应用（必选）

1. 记录应用构建、HEAD、Runtime、渠道和模型、预算及操作权限；确认独立测试配置有效、真实目录未被写入。
2. 创建 Fixture A 并提交干净基线；绑定本地工作区与测试项目，关闭外部同步。
3. 配置一个研发员工，明确工作区、模型、auto 权限；不设置 bypassPermissions。
4. 从文件菜单进入委派，预填定位；确认允许范围、验证命令、DoD、真实低风险决策和 local-user reviewer。
5. 派发后不手动改代码；若出现权限请求，处理并记录“人工介入”的次数、类型和时长。
6. 第一轮结束，检查原目录未变，Review 内能看到真实 Diff 和验证来源；即使第一轮很好，也按上述返工意见退回一次。
7. 验证新 executionId、同 sessionId／worktree、新交付版本、旧证据可读。
8. 在 Review 中逐项勾选 DoD、填写依据，再点击验收通过。确认通过后源目录仍未改变。
9. 点击应用，核对目标、版本和文件集合后确认；检查源目录内容 hash 一致、Git 无新 commit、没有 push。
10. 在源目录经用户授权独立复跑测试；检查任务完成遵守 DoD，关闭并重开应用后历史和结果可恢复。

通过标准：全程不人工编辑代码；一次返工有效；无源目录提前污染；原目录最终内容匹配审核版本；测试和责任链证据完整。若需要中途授权仍可算受控闭环成功，但不能标为“只在末尾 Review”。

### R02：仓库内文档修改 → 返工 → 应用（必选）

按 Fixture B 执行同一路径。人工核对保留章节、内容语义及错误示例，确认 Review 能清楚显示新增／删除。不能把 R01 通过视为文档路径已通过。

### R03：应用目标变化保护（必选，确定性也需真机检查）

在验收后、应用前，由测试操作者向源仓库增加一条未提交改动。点击应用应阻塞；该改动保持原样，Task 不被伪标 completed。人工自行恢复干净状态后重新预检与确认，不复用过期确认单。

### R04：崩溃恢复与兼容（必选，可用测试运行器）

仅在独立测试环境模拟 applying 期间中断；重开显示 recovery_required 或经 hash 核验后的 applied，不重复写入。再打开一个旧普通员工任务和旧交付，确认可读与原流程兼容。

## 6. 分阶段退出门禁

| 门禁 | 所需证据 | 放行结果 |
|---|---|---|
| G0 基线 | 三个原有研发测试、fixture 与隔离检查 | 可以实施新契约 |
| G1 契约 | 范围、快照、员工受限提交与权限拒绝通过 | 可以开发 Review UI |
| G2 可审阅 | 同页 Diff、真实证据标签、一次确定性返工 | 可演示 Review，不宣称可应用 |
| G3 可应用 | 精确应用、漂移拒绝、恢复与 DoD 回写 | 可申请真实模型试跑 |
| G4 可试用 | R01–R04 通过，完整仓库门禁和目标平台实际构建／打包烟测 | 仅放开验收过的范围和 Runtime 组合 |

## 7. 结果记录格式

每次运行在台账增加独立条目，禁止覆盖失败历史：

```text
runId / testId / startedAt(+08:00) / endedAt
commit / applicationBuild / OS / runtime / modelId
fixtureId / projectId / taskId / executionId / sessionId
baseCommit / snapshotId / contentHash / deliveryId+version / operationId
expected / actual / result(PASS|FAIL|BLOCKED|SKIP)
command / exitCode / logRef / screenshotRef
humanInterventions(count,type,reason) / tokenUsage / actualCostOrUnknown
reviewer / defectId / retestOf
```

- 日志脱敏，不记录 API Key、Authorization Header、原始私密配置；金额缺失写 unknown。
- 自动测试 PASS 需原始日志、退出码、对应提交；L4 PASS 还需人工 Review 记录和源目录 hash 核对。
- SKIP 不算 PASS；缺渠道授权是 BLOCKED；失败后重试成功也保留首次失败。
- 发布前所有 P0／P1 缺陷关闭并复验；未验收的 Runtime、文件类型、系统平台单独列出。
