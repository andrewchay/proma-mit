# MCP 工具调用的结果分类：局部证据

日期：2026-10-29；范围仅 MCP `callTool` 的失败语义，不代表资源读取、工具列举、真实远端 MCP 服务或打包应用验收已覆盖。

## 缺口

`mcp-client.ts` 的 `executeTool` 把所有失败压成一句：

```
return { content: `MCP 工具调用失败: ${message}`, isError: true }
```

MCP 服务端是外部进程或远程服务。一次 `callTool` 抛错**不能**说明工具没执行：请求可能已经送达并在服务端产生了副作用（发出邮件、写入远端记录、提交工单），只是响应在返回途中超时或连接断开。模型看到"调用失败"就会重试——在真实系统上是重复执行。同时这也丢掉了唯一可用的结构化判据：JSON-RPC 错误码。

## 本次改动

**共用骨架扩容**：`describeActionFailure` 增加可选 `classify` 参数，允许域内提供额外判据，保证"文案"和"归类结论"走同一个实现。这一条是被测试逼出来的——初版 `mcp-tool-outcome` 的文案函数内部重新调用了通用 `classifyActionFailure`，导致 JSON-RPC 错误码分支在文案侧根本走不到，同一错误会出现"文案说未执行、归来说未知"的错位。

**当前判据（2026-10-29 收口）**：

- 只有数字 JSON-RPC 错误码 `-32601 Method not found` 判为**未执行**；`-32600`、`-32602` 也可能由 SDK 在工具执行后的输出校验阶段抛出，与其余服务端错误码一样保持**结果未知**。
- 没有数字错误码时，不再凭 `Method not found`、`Invalid params`、权限拒绝等文案或系统错误码推断未执行；派发后的异常默认未知。
- `result.isError` 保留服务端原始诊断，不再压成通用错误。实际失败原因通过 `unknown_failed` 事件持久化，重启后仍能恢复。
- `-32601` 只有在完成事件成功落盘后才解除本次预登记，允许修正后重试；解除写入失败时继续保持门禁。
- SDK 的 task-required 前置守卫在派发登记前检查：命中时明确返回未执行，不调用服务，也不制造未知记录；已有 unknown 记录仍优先拦截。

## 证据

`mcp-tool-outcome.test.ts`（11 项）覆盖：`-32601` 未执行；`-32600/-32602/-32603/-32000/-32001` 未知；数字码以外的错误文案与 `EACCES` 不再放行；超时、中止、断连和无法归类异常均为未知；文案与分类一致。

`mcp-client.test.ts`（14 项）覆盖：工具错误文案及存储理由保留 `failed after dispatch`；`-32601` 后同参数第二次调用成功且服务调用两次；task-required 前置拒绝不触达服务且不产生 pending；成功、未知阻断和真实本地 stdio 启动/列举/关闭路径。

最终定向复验：`mcp-client` 14 项、`mcp-tool-outcome` 11 项零失败；Agent Runtime 全目录 121 个测试文件零失败；typecheck=0、biome 通过。全仓分四批覆盖 786 个测试文件，合计 5576 pass、47 skip、1 fail；唯一失败为可独立复现的 `academic/run-service` 本地执行器用例，与本次 MCP 修改无关，不能记为全仓全绿。

## 边界

- **不是业务回执**：`-32601` 只证明方法未执行；unknown 无法判断副作用，必须核对目标系统。
- **异常注入仍使用 stub**：真实本地 stdio 用例只覆盖启动、工具列举和关闭，没有对真实 stdio / HTTP MCP 服务制造执行后的超时、断连或输出校验失败。
- **task-required 只完成前置拒绝**：尚未实现任务式 MCP 调用链，文案要求改用支持任务的调用方式。
- **资源读取与工具列举未分类**：这些只读操作仍走各自日志路径，不纳入外部写动作门禁。
- **进程回收与打包验收未扩大**：本切片不改变回收机制，也不替代真实打包应用中的 MCP 子进程回收验收。
