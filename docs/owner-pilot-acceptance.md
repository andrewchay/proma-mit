## 打包渠道确认

若使用 `dist:dev`，Dev 渠道**默认关闭** Goal、主动调度、Pilot、AI 员工心跳等后台任务，Owner 自主执行无法运行——那种包只能验证手动路径。

## 一、第 1 步：修订版本绑定

**前置**：任一项目跑完一次完整交付，成果在对话中可见。

| 编号 | 操作 | 期望 | 结果 |
|---|---|---|---|
| R1-1 | 在交付成果旁点「要求修改」，输入修改意见并发送 | 规划请求发出，模型响应**不含** `messageId`/`artifactHash` | |
| R1-2 | 检查生成的计划 | `deliveryFeedbackAssessment.messageId` 等于用户选中的那条交付消息 ID | |
| R1-3 | 重复点击「要求修改」 | 只产生一条修订意图，不重复派工 | |

**关键证据**：模型原始响应中不出现 64 位十六进制标识。若出现，说明走了历史路径，需确认 `deliveryFeedbackBindingVersion` 是否真的传了 `1`。

## 二、第 2 步：冻结验收标准

**前置**：新建项目，目标包含五类硬要求。

建议目标（与探针一致）：

> 制作一份书架盘点工作单，打印后供两名志愿者在现场使用

- 约束：`A4纸打印，四边15毫米边距`、`现场需在45分钟内完成`
- 验收标准：`打印后必须为一页`、`四个书架逐架复点并记录差异`、`表格底部预留签字栏`

| 编号 | 操作 | 期望 | 结果 |
|---|---|---|---|
| R2-1 | 提交目标后查看规划响应 | `criteriaTrace` 含六条（objective 1 + constraints 2 + acceptance 3） | |
| R2-2 | 逐条核对 | 五类硬要求全在：一页 / 45 分钟 / 两名 / 逐架 / 签字 | |
| R2-3 | 检查 `assessCriteriaCoverage` | `uncovered` 为空，`criticalUncovered` 为 0 | |
| R2-4 | 故意给模糊目标（如「做个表格」） | 模型省略 `criteriaTrace` 而非编造 | |

**已知不稳定性**：同一模型两次运行结果不同。实测中曾漏掉 `objective` 里的「两名」。若复现，系统应以「目标正文未被任何步骤承接」拒绝，而不是静默通过。

## 三、第 3 步：硬要求接入验收链

**前置**：接续第 2 步。

| 编号 | 操作 | 期望 | 结果 |
|---|---|---|---|
| R3-1 | 查看材料化后的任务 | 该步骤 `acceptanceCriteria` 包含目标硬要求原文 | |
| R3-2 | 执行完成后查看评审 | Reviewer 逐项检查了这些硬要求，不是只查步骤原有标准 | |
| R3-3 | 构造一项未满足（如打印成两页） | `verdict` 不能是 `accept` | |
| R3-4 | 检查 `not_verified` 项 | 不能被当作 `met` 放行 | |

**注意**：打印页数验证器**本轮未实现**。若模型声称「一页已核验」但无真实渲染证据，应视为缺陷——`verification` 为 `unverified` 时不得标记为已验证。

## 七、发布门槛

| 指标 | 门槛 |
|---|---|
| 错报完成 | 0 次；任一例暂停扩大范围 |
| 一次交付合格 | 10 题至少 8 题，两类各至少 4/5 |
| 一轮反馈后合格 | 10 题至少 9 题；错版与重复派工为 0 |
| 用户负担 | 至少 6/10 题少一次干预 |
| 时间与费用 | 0 次超授权；未知费用单列 |
| 并发与恢复 | 0 次跨项目串线、重复扣费、错误释放占额 |

**可交付率必须与错报一起看**，防止系统靠一直「待验证」取得零错报。
