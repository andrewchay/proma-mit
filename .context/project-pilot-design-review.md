## 总结

支持 P0 先行、系统级 Pilot、顶部一级收件箱三个已确认方向。但需修正状态建模、收件箱职责和 P1 自动化边界，再作为实施基线。

## 开工前应修正

1. P1 范围冲突：2.1 明确所有变更需逐条确认，3.2、P1 第3项与验收却允许授权后自动指派。建议统一为 P1 只读分诊、建议、人确认后执行；限额自动编排移 P2。创建、指派、返工均可能导致付费运行和文件修改，不应一概归为低风险。
2. 收件箱不是第二套审批系统：只做统一投影与动作入口，权威状态和权限校验仍在原服务。至少需要源类型/源ID、项目/任务ID、处理者、源版本、有效期、状态、允许动作；执行前重校验、幂等处理、多入口同步。重启后不能重放已失效的权限或 AskUser 请求。
3. 任务与项目共用事实源和派生规则，不共用线性状态机。任务按适用流程展示执行、审阅、返工、验收、应用；非代码任务可不适用应用。项目汇总多任务并行状态、阻塞、里程碑，不能冒充单任务流水线。阻塞、失败、取消需独立表达，返工保留轮次。
4. IA 边界：依赖只在任务中维护，协作可引用；DoD 定义在配置、证据与验收在任务/协作；风险规则在配置、实际风险在概览/任务；AI 成本至少按项目/任务/时间聚合，不仅是日志。
5. 一级导航稳定，不采用“无数据即隐藏、有数据自动出现”。稳定保留五组；未启用能力隐藏，已启用但为空使用空状态。
6. Inbox(N) 表示待当前用户处理的有效事项，而非所有事件。失败和 DoD 未满足仅在需要人行动时进入；同一事项不同视图共用身份，不重复计数。安全审批不得因节流而丢弃。
7. 就地处理应改为无需丢失上下文：简单操作内联，交付验收用抽屉/审阅面板查看差异、验证、范围及版本再确认；不能为降低点击数压缩安全审阅。
8. Pilot 保持系统服务定位：去除“PM agent 档案/员工式角色”等歧义，改为策略配置、运行记录、摘要生成配置。确定性分诊不依赖模型会话或 Git 绑定；模型摘要和员工执行按需使用工作区。
9. R01 只证明该场景验证通过，不足以证明执行层普遍可靠。P0 不改执行核心，但聚合服务、IPC 适配可能必要，不能预先承诺“不动 IPC”。

## 推荐 P0 最小范围

- 稳定导航重组、任务详情可达、验证区常驻、范围阻塞后的重新交付入口。
- 首批收件箱源：交付待验收、权限/AskUser、确实需要人拍板的决策。
- 任务级适用流程进度与项目级状态汇总；统一事实源。
- 不含 Pilot、自动编排、团队大改、项目初始化自动执行。

## 验收修订

固定 R01 起点、终点及计数口径，点击数仅作效率指标；首次用户检验可发现性，原用户复跑检验效率，不能互相替代。增加多任务并行、返工/范围阻塞、重复操作/过期审批/重启恢复场景。确认不绕过安全闸门、不重复执行、不丢失待办。非代码项目若在产品支持范围，也应验证无需 Git 和应用步骤。
